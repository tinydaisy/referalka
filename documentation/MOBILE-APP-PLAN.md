# MOBILE-APP-PLAN.md — Своё мобильное приложение ПЛЮСОН (App Store + Google Play)

> Статус: **план / проектирование** (2026-06-27). Код ещё не пишется.
> Идея: превратить ПЛЮСОН из «Telegram-бот + Mini App» в **самостоятельное приложение**,
> где ПЛЮСОН становится **4-й площадкой** наравне с TG / VK / MAX.

---

## Концепция — три слоя

Все три слоя — единое целое (по решению владельца: «одно без другого не существует»).
Соцсеть без событий бессмысленна; события без коллабораций — это просто старый ПЛЮСОН.
Строим **поэтапно**, потому что физически нельзя сделать всё разом и каждый слой опирается на предыдущий.

### 1. Бесплатный уровень — зрители (соцсеть)
- Свой профиль-карточка (по сути карточка основателя, но для зрителя)
- Общение и переписки друг с другом
- Подписки на других
- Посещение чужих событий (просмотр, вход, регистрация)
- Список посещённых событий (история)
- Лента

### 2. Платный уровень — клиенты ПЛЮСОН
- Создание своих событий
- **Чаты события прямо в приложении** — это и есть 4-я площадка
- Регистрация в событие возможна с **4 площадок** (TG / VK / MAX / ПЛЮСОН)
- Хаб событий клиента + вход в конкретное событие
- Вся внутрянка события: программа, время, подарки, рефералка

### 3. Коллабораторная
- **Не видна зрителям** — только внутри участников
- Весь существующий collab-функционал

> Связка с вебом сохраняется: настраивать события удобнее в веб-версии,
> но базово можно и в приложении. Приложение = ещё один клиент к текущему API.

---

## Ключевое преимущество: рассылки без банов и лимитов

На чужих площадках (Telegram, VK, MAX) рассылки **режут**: лимиты на скорость,
баны за «спам», блокировки ботов, ограничения на сообщения людям, которые
давно не писали. Из-за этого клиент теряет связь со своей же аудиторией.

**В своём приложении ПЛЮСОН этих ограничений нет.** Поскольку канал доставки —
наш собственный (push + сообщения внутри приложения, а не чужой Bot API),
клиент может **свободно слать сообщения тем, кто:**
- интересовался событием (открыл, но не зарегистрировался),
- регистрировался на событие,
- посещал прошлые события,
- подписан на него как на основателя.

Никаких банов за рассылку, никаких лимитов скорости от внешних платформ,
никакой потери базы из-за блокировки бота. Это превращает ПЛЮСОН-площадку
в **самый надёжный канал связи клиента с аудиторией** — то, ради чего
многим и нужна своя 4-я площадка.

> ⚠️ Юридически/этически рассылки остаются на основе **согласия** (человек
> сам открыл/зарегистрировался на событие клиента = выразил интерес). Это не
> «спам кому угодно», а законная коммуникация с собственной аудиторией —
> просто без искусственных технических ограничений чужих платформ. Сторы
> (Apple/Google) к таким push-уведомлениям претензий не имеют, пока есть
> возможность отписаться в настройках приложения.

## Два главных принципа архитектуры

### Принцип 1: приложение = ещё один клиент к существующему API
Бэкенд (FastAPI), БД и бизнес-логика **уже готовы на ~60%** того, что нужно.
Это НЕ разработка с нуля. Приложение встаёт рядом с Mini App как 4-й фронт.
Веб остаётся для настройки событий.

### Принцип 2: ПЛЮСОН становится 4-й площадкой в БД
```
platforms: telegram, vk, max, + pluson   ← новая строка
```
- Нативный аккаунт = `platform_users(platform_slug='pluson', platform_user_id=<наш user id>)`
- Регистрация в событие с 4 площадок — `event_participants` уже полиморфен по контактам
- Чаты события на платформе `pluson` — новая сущность, но концепция
  `event_chat_messages` + подсчёт баллов уже есть

## Технология

**React Native + Expo.**
- Один код → iOS (App Store) + Android (Google Play)
- Push-уведомления из коробки (Expo Notifications) — критично для соцсети и событий
- Переиспользуем бизнес-логику и структуру из Mini App (вёрстку — заново, логику — нет)
- Expo EAS собирает и публикует в оба стора без своего Mac

Альтернатива Flutter — отклонена: весь фронт пришлось бы писать заново, ничего из React не переедет.

## Что переиспользуется, а что строится с нуля

| Слой | Готово (переиспользуем) | Строим с нуля |
|---|---|---|
| Хаб событий | API событий, `events`, хаб-логика, внутрянка (программа/подарки/рефералка) | Нативные экраны RN |
| Профиль-карточка | `clients` (карточка основателя), `contacts`, фото в R2 | Публичный профиль **зрителя** (сейчас зрители — просто `contacts`, без публичного профиля) |
| Соцсеть | `direct_messages` как фундамент переписок | Подписки (новая таблица), лента, реалтайм-чат, публичные профили зрителей |
| Чаты события (4-я площадка) | `event_chat_messages`, проверка членства, баллы за активность | WebSocket-инфраструктура, само хранение чата |
| Коллабораторная | Весь функционал уже в вебе | Нативные экраны + гейтинг видимости (не видна зрителям) |

## Дорожная карта по этапам

### Этап 0 — Фундамент (инфраструктура)
- Аккаунты разработчика: **Apple $99/год**, **Google $25 разово**
- Expo EAS проект, каркас навигации
- **Нативная авторизация ПЛЮСОН** (новое) — вход телефон/email + код.
  Обязателен **Sign in with Apple** (Apple требует при любом соц-входе; Google — нет)
- Добавить `pluson` в `platforms`, научить `platform_users` хранить нативные аккаунты
- ⚠️ **Отдельный сервер под реалтайм** — текущий (RAM ~2ГБ, билд падает по OOM) мессенджер не потянет

### Этап 1 — Зрительский слой (read + профиль)  → первый релиз в стор
- Профиль зрителя (расширить `contacts` или новая таблица `user_profiles`)
- Хаб событий (переиспользуем API) — нативные экраны
- Чужие события: просмотр, вход, регистрация
- История посещённых событий (`event_participants` уже хранит)
- Подписки (новая таблица `follows`)
- **Проходит ревью уже здесь**, если есть реальная ценность (push о событиях)

### Этап 2 — Общение (соцсеть оживает)
- Лента (события тех, на кого подписан + активность)
- Личные переписки. Старт — **поверх `direct_messages` + polling** (без WebSocket). Позже — WebSocket
- Push-уведомления
- **Рассылки по своей аудитории без банов/лимитов** — клиент свободно шлёт push +
  сообщения внутри приложения тем, кто интересовался/регистрировался/посещал события
  или подписан на него. Канал наш → нет ограничений чужих платформ (см. раздел «Ключевое преимущество»).
  Обязательна возможность отписаться в настройках (требование сторов)
- ⚠️ **Обязательно для обоих сторов (UGC):** жалобы на контент и пользователя,
  блокировка пользователя, EULA с нулевой терпимостью, реакция на жалобу ≤24ч.
  Без этого — отказ

### Этап 3 — Клиентский слой (события внутри приложения, 4-я площадка)
- Создание/управление событием из приложения (минимум; полная настройка — в вебе)
- **Чаты события прямо в приложении** — здесь нужен полноценный WebSocket-реалтайм
- Регистрация в событие с 4 площадок
- Внутрянка: программа, подарки, рефералка — переиспользуем

### Этап 4 — Коллабораторная
- Закрытый слой только для участников (гейтинг: не видна зрителям)
- Весь collab-функционал → нативные экраны

## Узкие места (где будет реально трудно)

1. **Реалтайм-чаты = вы становитесь мессенджером.** Самый тяжёлый кусок.
   Нужна WebSocket-инфраструктура и нормальный сервер. Поэтому он в Этапе 3,
   но архитектуру закладываем сразу.
2. **Слабый сервер.** Под мессенджер и push нужна отдельная инфраструктура. Заложить в бюджет.
3. **Модерация UGC.** Не код, а обязательные механизмы (жалобы/блок/EULA). Этап 2, иначе отказ.
4. **Оплаты тарифов.** См. раздел «Деньги и оплаты» — решается выносом оплаты в веб.

## Деньги и оплаты

### Золотое правило сторов (одинаково у Apple и Google)
**За что платят → тем платёжным методом обязан быть:**

| Что продаёте | Чем обязаны платить | Комиссия стора |
|---|---|---|
| **Цифровое** внутри приложения (подписка на функции, премиум, виртуальные баллы/подарки) | **Только встроенный биллинг** (Apple IAP / Google Play Billing) | **15–30%** |
| **Физическое / реальные услуги офлайн** (билет на живое мероприятие, товар) | Любая своя платёжка (ЮKassa, Продамус, карта) | **0%** |
| **B2B / SaaS снаружи приложения** | Своя платёжка на сайте | **0%** |

Обходы караются баном (Apple особенно жёстко).

### Как это ложится на 3 слоя ПЛЮСОН

**1. Зрители (бесплатно)** — денег нет, проблемы нет.

**2. Клиент ПЛЮСОН (платная подписка на тариф)** — главный денежный поток:
- Оплата тарифа **внутри приложения** → обязателен биллинг стора → **минус 15–30%**. Больно.
- Оплата **на сайте** (где клиент и так настраивает события), в приложении — только пользование → **0%**.
- ➡️ **РЕШЕНИЕ: оплату тарифов держать в вебе. В приложении НЕТ кнопки «купить тариф».**
  Для B2B/SaaS это разрешено. Внутри приложения максимум текст «оформить тариф на pluson.ru»,
  **без кнопки оплаты и без активной ссылки на платёжку** (Apple запрещает даже зазывать на внешнюю оплату; Google мягче, но не рисковать).

**3. Билеты на события / VIP-тарифы участникам** (уже есть `event_tariffs` + вебхук «оплатил»):
- Билет на **живое/онлайн-мероприятие = реальная услуга** → своя платёжка, **0% комиссии**.
  Основной денежный оборот событий идёт мимо сторов — большой плюс.

**Реферальные «подарки»** — не покупаются за деньги, зарабатываются действиями → под биллинг не попадают.
Осторожность только в формулировках (не «плати за приглашения»).

### Куда реально приходят деньги
- **Своя платёжка (ЮKassa / Продамус / CloudPayments)** → деньги **напрямую на ваш счёт**, полный контроль. Рабочий путь для РФ.
- **Биллинг сторов** → собирает Apple/Google, удерживают комиссию, выплата раз в период.
  Для РФ-разработчиков выплаты от Apple/Google осложнены санкциями/валютным контролем — отдельная головная боль.

### Итог по деньгам
- Тарифы клиентов — оплата в вебе, своя платёжка, **0% комиссии**, деньги напрямую.
- Билеты/VIP на события — своя платёжка (услуги), **0% комиссии**, деньги напрямую.
- **Встроенный биллинг сторов, по сути, не нужен вообще** — мы не продаём чисто-цифровой премиум за деньги прямо в приложении.
- При правильной архитектуре комиссия 15–30% **обходится легально**: монетизация = SaaS (веб) + услуги-события (платёжка).
- Единственное, за чем следить: **никаких кнопок оплаты цифровых функций внутри приложения**.

## Магазины: App Store vs Google Play

| | Google Play | App Store |
|---|---|---|
| Аккаунт | **$25 один раз** | $99/год |
| Скорость ревью | часы–пара дней | 1–3 дня (с UGC дольше) |
| Обёртка вокруг веба | пропускают спокойно | заворачивают (правило 4.2) |
| Свой вход без Apple/Google | можно | **Sign in with Apple обязателен** при любом соц-входе |
| Оплаты | свой биллинг для цифры, строгость ниже | жёстко, обходы банят |
| Ревью | в основном автомат | живой ревьюер придирается |

### Где Google мягче
- Не требует Sign in with Apple — свой вход (телефон/email + код) достаточно
- WebView-обёртку терпит (то, за что Apple бьёт по 4.2)
- Ревью чаще автоматическое, цикл быстрее

### Где Google НЕ мягче (прямо наш случай)
⚠️ **UGC и переписки** — обе площадки требуют одно и то же:
- жалобы на контент и на пользователя
- блокировка пользователя
- политика против оскорблений + реакция на жалобы
- политика конфиденциальности
- Google: **Data safety** — обязательная форма-декларация (что собираем: сообщения, контакты, профиль; зачем). Заполняется руками, проверяют.

Дополнительно у Google:
- **Целевой API-level** Android поднимают каждый год — держать актуальным, иначе не примут обновления
- **Закрытое тестирование** для новых аккаунтов — часто требуют прогон через тест-группу (~12–20 чел., ~2 недели) до публичного релиза

### Стратегия выхода
- **Сначала Google Play** — дешевле, быстрее, прощает обёртку и свой вход. Полигон для проверки гипотезы (Этап 1).
- **App Store вторым заходом** — когда добавим Sign in with Apple и механизмы модерации.
- **Модерацию UGC делать в любом случае** — единственное, что Google не прощает, и ровно то же требует Apple. Один раз → закрывает обе площадки.

## Честная оценка

- **Не с нуля** — бэкенд, БД и логика готовы на ~60%. Большая фора.
- **Объём** — новый продукт, реалистично **6–12 месяцев** поэтапного выката.
  Первый релиз в стор (Этап 1) — реально за **1.5–2 месяца**.
- **Магазины пропустят** — соцсеть с реальной ценностью Apple/Google любят больше обёрток.
  Главное — модерация UGC и не нарушать правила оплат.
- **Самое сложное — не приложение, а мессенджер и инфраструктура под него.**
- **Главная ценность для клиента** — своя площадка снимает баны и лимиты чужих
  платформ на рассылки по своей аудитории (см. «Ключевое преимущество»). Это весомый
  аргумент перейти на платный тариф ПЛЮСОН.
