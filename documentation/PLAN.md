### [ ] Медиа-кит организатора/спикера — переносимая визитка для чужих событий (запланировано 2026-06-26)

**Идея.** Сделать на платформе «медиа-кит» — единую карточку человека (организатора/спикера), которую можно отдавать **организаторам других конференций**. То есть собранная один раз информация о себе переиспользуется в чужих, уже существующих событиях.

**Что входит в медиа-кит:**
- Регалии / достижения
- Каналы (соцсети, медийные активы с числом подписчиков)
- Тема(ы) выступления
- Подарок (лид-магнит/бонус, который человек даёт аудитории)
- Фото

**Зачем.** Сейчас эти поля живут внутри `collaborators` / `event_collaborators` и привязаны к конкретному событию клиента. Нужно, чтобы человек заполнил профиль один раз, а организатор другого события мог подтянуть его медиа-кит к себе (по ссылке/коду), не вбивая данные вручную.

**На подумать при реализации:**
- Источник данных переиспользует уже существующие поля: `collaborators` (фото, регалии, соцсети, `media_assets`), `event_collaborators` (тема, подарок) — не плодить дубли.
- Механика передачи: публичная карточка-ссылка `pluson.ru/...` + импорт «добавить спикера из медиа-кита» в чужое событие. Возможно через `access_code` коллаба или отдельный публичный slug.
- Пересечение с уже готовыми эндпоинтами `landing-widget` и кабинетом спикера `/speaker/<slug>` — переиспользовать, а не делать с нуля.

### [ ] Партнёрская регистрация спикера через кабинет привязывает код НЕ к спикеру (отложено 2026-06-04)

**Симптом.** Когда спикер передаёт ссылку+код доступа своему **ассистенту**, ассистент входит в кабинет `/speaker/<slug>` и регистрируется партнёром на стороннем ресурсе — партнёрский код привязывается к **ассистенту**, а не к спикеру. Либо ассистенту в боте приходит «вы не привязаны ни к какому спикеру, код получить не удалось».

**Корень.** Весь партнёрский флоу ([backend/app/services/partner_service.py](../backend/app/services/partner_service.py)) идентифицирует человека по `tg_id` того, кто физически нажал ссылку/вернулся в бот, а не по спикеру из кабинетной JWT-сессии:
- `run_started_partner` (строка ~287) делает `upsert_contact_with_identity(tg_id=нажавшего)` → контакт создаётся ассистенту.
- кнопка на лендинг получает `?pluson_cid=<контакт нажавшего>` → webhook GetCourse пишет код этому контакту.
- `send_partner_done_tg` (строка ~487) ищет контакт по `tg_id` вернувшегося.
- Вдобавок ссылка кабинета содержит `prtp_<first_referrer_contact_id>` ([speaker_cabinet.py:723](../backend/app/api/speaker_cabinet.py)) — это рефовод спикера, а не сам спикер. Тип `prtp_` спроектирован под «привести нового партнёра под рефовода», а не «зарегистрировать самого спикера».

**Нужное поведение (подтверждено):** код должен лечь в контакт **самого спикера**, кто бы ни нажал (сам спикер или ассистент).

**План правки** (новый тип `prts_<speaker_contact_id>` — «partner-self»):
1. Кабинет ([speaker_cabinet.py:723](../backend/app/api/speaker_cabinet.py)) — для ссылки самостоятельной регистрации спикера слать `prts_<contact_id спикера>` (из `c.contact_id`), не `prtp_<рефовод>`.
2. `resolve_partner_entry` ([partner_service.py](../backend/app/services/partner_service.py)) — добавить ветку `prts_` с `target_contact_id` спикера, отдельным от tg-идентификации нажавшего.
3. `run_started_partner` — при `prts_` НЕ делать upsert по tg_id нажавшего; работать с зафиксированным контактом спикера. Кнопка на лендинг → `?pluson_cid=<контакт спикера>`.
4. Возврат — `partner_done_s_<speaker_contact_id>` вместо поиска по tg_id вернувшегося, чтобы код показывался и ассистенту, и спикеру.
5. Обработчики `/start` ([bot/handlers/start.py](../backend/bot/handlers/start.py)) + VK-consumer ([bot/vk_main.py](../backend/bot/vk_main.py)) — понимать новый префикс.

**Что НЕ ломается:** отображение кода в кабинете (`speaker_external_ref_param`) уже читается из контакта спикера и работает. Чинить надо только ЗАПИСЬ кода и возврат в боте.

## ⚠️ Ключевые архитектурные принципы (не нарушать!)

### Иерархия Контактов — пять связанных таблиц (миграция 036 от 26.04.2026)

```
platforms (telegram/vk/max справочник)
   ↑
contacts (ЧЕЛОВЕК) ← ref_code, email, phone, имя
   ↓
platform_users (его аккаунт на платформе) ← username, tg_id/vk_id
   ↓
platform_user_channels (подписка аккаунта на канал клиента)
   ↑
channels (боты/группы клиента)
```

- Один человек = одна запись в `contacts`. Если у него TG и VK — две `platform_users`, ссылающиеся на тот же `contact_id`.
- Реф-код, email, phone, теги — на уровне человека (`contacts`), а не аккаунта.
- Username, tg_id — на уровне аккаунта (`platform_users`).
- Один аккаунт может быть в нескольких каналах клиента (например, в двух его TG-ботах) — каждая подписка отдельной строкой в `platform_user_channels`.
- Платформа — справочник `platforms` (нельзя ввести опечатку). У платформы метаданные: иконка, цвет, лимит сообщения.
- Автомердж при импорте: ищем существующий contact по email/phone, привязываем новую идентичность. Не нашли — создаём. Дубли — через ручной мердж в UI.

### Один реф-код на человека (миграция 032 от 26.04.2026, переехал в contacts миграцией 036)
- Источник истины — `contacts.ref_code` UNIQUE
- Поля `event_participants.ref_code` и `conf_speaker_events.ref_code` УДАЛЕНЫ (миграция 032)
- Резолв реферера всегда через `JOIN contacts WHERE c.ref_code = referrer_ref_code`
- Резолв спикера: `c.ref_code → collaborators.contact_id → event_collaborators`
- В `contacts.first_referrer_contact_id` — кто впервые привёл (вместо `first_referrer_ref_code`)
- В `event_participants.referrer_ref_code` остаётся per-event реферер
- Слитые реф-коды — в `contacts.merged_ref_codes` JSONB

### Мультиплатформа — каналы доставки (миграции 033+034+036)
- `bot_token` живёт в `channels` (per-канал), у клиента может быть несколько ботов
- Подписка/отписка — в `platform_user_channels` per-канал, не на самом контакте
- `clients.bot_token` УДАЛЕНО (033), `platform_users.is_unsubscribed` УДАЛЕНО (034)
- `platform_users.platform` возвращена как `platform_slug` → `platforms(slug)` (036)
- Составные FK гарантируют совпадение платформ: TG-аккаунт нельзя подписать на VK-группу

### Реф-программа — вкладка события, не отдельный раздел (миграция 035 от 26.04.2026)
- Раздел «Рефералки» из сайдбара убран
- Реф-программа — вкладка внутри карточки **любого события** (мероприятия и конференции)
- Подвкладки: Подарки (пороги → лид-магнит) / Материалы (картинки для шеринга) / Шаблоны (welcome + share text)
- Лид-магниты — общая база per-client (`lead_magnets`), используются как подарки в реф-программе любого события

#### 1.2.А Хаб организатора

- [ ] Контекст: открывается при `/start` без `startapp` или при тапе «‹ Назад» из события
- [ ] Шапка: фото клиента + имя + одна строка позиционирования

  - [ ] Секция «🔴 Сейчас идёт» (события клиента, у которых `start_at <= NOW() <= end_at`)

**А. ДО регистрации (`event_participants.is_registered = false` или нет записи):**

**В. ПОСЛЕ завершения (`end_at < NOW()` или `events.status = 'ended'`):**

### 3.Y Своя вебинарная комната через Zoom RTMP (идея, обсуждено 2026-04-30)

**Суть:** убрать зависимость от внешних стримов (YouTube Live, VK Видео) — зритель смотрит трансляцию прямо в Mini App / на лендинге, в нашем брендинге. Ведущий продолжает работать в привычном Zoom.

**Схема:**
1. Ведущий запускает Zoom как обычно (Webinar или Meeting с включённым Live Streaming)
2. Zoom стримит на наш RTMP-эндпоинт через встроенную функцию «Live Stream to Custom Service» (RTMP URL + stream key уникальный per-event)
3. На сервере — RTMP→HLS конвертер (MediaMTX / SRS / nginx-rtmp)
4. Mini App во вкладке «Программа» / «Эфир» показывает HLS-плеер (hls.js) поверх нашей вёрстки
5. Чат — отдельным слоем сбоку (через WebSocket, упор на текст без видео-интеракции)

**Преимущества:**
- Зритель не ставит Zoom, не уходит из Mini App
- Полный брендинг (логотип ПЛЮСОН, цвета, чат с реакциями, статус «идёт сейчас»)
- Ведущий работает в Zoom — без переучивания
- Контроль над данными (кто смотрел, сколько, какие комментарии)

**Тред-офф:**
- Задержка 10-30 секунд (HLS) против 200 мс у WebRTC. Для вебинара ОК (зритель пассивный), для интерактива — нет
- Нагрузка на сервер: трафик HLS-сегментов на каждого зрителя. На 1000 одновременных — нужен CDN или отдельный VPS под видео

**Что нужно сделать:**
- [ ] Поднять MediaMTX / SRS на отдельном поддомене (`stream.pluson.ru`) — отдаёт HLS на 8888, принимает RTMP на 1935
- [ ] Таблица `event_streams` (event_id UNIQUE, stream_key UNIQUE, rtmp_url, hls_url, is_live, started_at, ended_at) — связка события с потоком
- [ ] API: `POST /api/v1/events/{id}/stream/start` (создаёт stream_key, отдаёт RTMP URL+key для копи-пейста в Zoom), `POST /stream/stop`, `GET /stream/status`
- [ ] Дашборд клиента: вкладка «Эфир» в карточке события — показ RTMP URL/Key + кнопка «Начать эфир» / «Завершить»
- [ ] Mini App: новая вкладка «📺 Эфир» (или замена `stream_url` в Программе) с HLS-плеером, появляется только когда `is_live=true`
- [ ] Чат: таблица `event_chat_messages` (event_id, contact_id, text, created_at) + WebSocket-эндпоинт `/ws/event/{id}/chat`
- [ ] Запись эфира: MediaMTX умеет писать MP4 — после завершения сохранить ссылку в `events.recording_url`, показать на лендинге как «Запись»

**Альтернативы (на случай если RTMP-схема не зайдёт):**
- Zoom Web SDK — встраивает Zoom-плеер в iframe внутри Mini App. Меньше работы, но Zoom-UI поверх нашего, частичный брендинг
- LiveKit / 100ms / Daily.co — полная замена Zoom (WebRTC SFU), но ведущий должен переучиваться
- Просто принимаем YouTube/VK Live в `events.stream_url` (текущий MVP-подход)

### 3.Z Mini App во ВКонтакте для VIP-клиентов (идея, обсуждено 2026-05-05)

**Суть:** дать VIP-клиенту возможность подключить наш Mini App не только в свой Telegram-бот, но и во ВКонтакте — как VK Mini App в его сообществе. Аудитория VK у некоторых клиентов больше, чем в Telegram.

**Почему это не «галочка», а отдельный продукт:**
- Текущий `mini-app/` написан под Telegram WebApp SDK (`@telegram-apps/sdk`). VK Mini Apps — отдельная платформа со своим SDK (`@vkontakte/vk-bridge`), своей авторизацией (`VKWebAppGetUserInfo` / Launch Params с подписью), своей модерацией.
- Фундамент в БД уже заложен (миграция 036): `platforms` содержит `vk`, `channels` поддерживает `platform_slug='vk'`, `platform_users` — `vk_id`. Маппинг данных готов, фронта и адаптера бэка под VK нет.

**Что потребуется от VIP-клиента:**
- Сообщество VK (паблик/группа) — VK Mini App вешается на сообщество, без него никак.
- Регистрация приложения на vk.com/dev → `app_id` и секретный ключ, прохождение модерации VK.
- Подключение приложения к сообществу через настройки сообщества → «Приложения».

**Что нужно сделать у нас:**
- [ ] Отдельная сборка `mini-app` под VK (alias `mini-app-vk/` или флаг сборки) с заменой Telegram SDK на `vk-bridge`.
- [ ] Адаптер авторизации: верификация Launch Params VK (HMAC-подпись по секрету), выдача нашего JWT по `vk_user_id` → `platform_users (platform_slug='vk')` → `contacts` через тот же мердж по email/phone.
- [ ] Бэкенд: эндпоинты `/api/v1/public/...` и `/api/v1/participants/miniapp/me/events` принимают `vk_id` так же как `tg_id` (сейчас завязано на TG).
- [ ] Канал доставки в `channels` для VK — отправка сообщений через VK Callback API / Bots Long Poll (рассылки и системные уведомления через сообщество).
- [ ] В дашборде `/dashboard/channels` — wizard подключения VK-сообщества (по аналогии с `connect-telegram-bot`): ввод community access token → `groups.getById` → upsert в `channels`.
- [ ] Гейт по тарифу: `tariffs.allow_vk_mini_app BOOL` (по аналогии с `allow_custom_bot`).
- [ ] Хостинг: VK требует HTTPS на собственный домен, проксируется через iframe внутри vk.com — нужно учесть CSP / `frame-ancestors`.

**Открытые вопросы:**
- Делать ли единый кодовый пакет с условной компиляцией (Telegram/VK через флаг) или два отдельных репо/билда. Скорее два билда — слишком много расхождений в SDK.
- Как разруливать «один человек = один контакт» если он пришёл и из VK, и из Telegram (мердж по email/phone уже есть, но в VK email не всегда отдаётся — требуется отдельный scope).
- Нужен ли в VK свой селектор-аналог `@pluson_bot` (общий VK-Mini-App ПЛЮСОНа) или сразу делать только под VIP-клиентов с их сообществами.

**Когда делать:** не в MVP. Откладываем до момента, когда у VIP-клиентов появится реальный спрос «у меня в VK аудитория больше, чем в TG, хочу там тоже». Сейчас VK можно использовать только как канал рассылок (и то — `channels` готовы, но рассыльщик под VK API ещё не написан).

### 3.П Приём оплаты за мероприятия клиента (Продамус pass-through, обсуждено 2026-05-07)

## ЭТАП 4 — РЕФАКТОРИНГ БД (после конференции)

> Цель: поддержка нескольких ботов, мультиплатформенность, правильная иерархия Контактов

### Концепция

Полная иерархия после миграций 033/034/036:
- `platforms` — справочник платформ (telegram/vk/max + метаданные).
- `contacts` — ЧЕЛОВЕК (один на клиента, ref_code, email, phone).
- `platform_users` — АККАУНТ человека на платформе (один человек может иметь несколько идентичностей: TG + VK).
- `channels` — каналы клиента (его боты/группы).
- `platform_user_channels` — подписка идентичности на канал клиента.

Терминология которую нужно соблюдать везде:
- **Клиенты** → таблица `clients` (пользователи платформы ПЛЮСОН)
- **Контакты** → таблица `contacts` (все люди в базе Клиента, после миграции 036)
- **Идентичности** → таблица `platform_users` (аккаунт человека на платформе)
- **Коллабораторы** → таблица `collaborators` (подмножество Контактов: спикеры, партнёры)
- **Спикеры** → таблица `event_collaborators` (роль Коллаборатора в конкретном событии)
- **Участники** → таблица `event_participants` (Контакты зарегистрированные в событии)

### Иерархия сущностей

```
platforms (справочник)
    ↑
Контакты (contacts) — человек
    ├── Идентичности (platform_users) — TG/VK/MAX-аккаунты человека
    │       └── Подписки (platform_user_channels) — на каналы клиента
    ├── Коллабораторы (collaborators) ← подмножество Контактов (FK contact_id)
    │       └── Спикеры (event_collaborators) ← роль в конкретном событии
    └── Участники (event_participants) ← Контакты в событии (FK contact_id)
```

### ⚠️ Нерешённые вопросы по рассылкам

**1. Аудитория — кому слать**
Сейчас в `broadcast_templates` и `broadcast_schedules` есть `audience_include` / `audience_exclude` — это отвечает на вопрос «кто». Значения: `all_event`, `all_client`, `registered_event` и т.д. Это остаётся.

**2. Каналы — через какой бот слать**
Сейчас одно поле `channel_id → channels` — это значит рассылка идёт через один конкретный бот. Но если рассылка «всей базе» — человек может быть в двух ботах, и надо слать в оба.

Варианты которые надо выбрать:
- `channel_id = NULL` → слать через ВСЕ каналы где Контакт подписан и не отписался
- `channel_id = конкретный` → слать только через этот бот
- Или отдельное поле `send_to_all_channels BOOLEAN`

**3. Дедупликация при рассылке по всем ботам**
Если Вася в двух ботах и рассылка идёт по всем — он получит два одинаковых сообщения. Нужно решить: это нормально или нужна дедупликация (слать только через один, например первый подключённый)?

**Решено:**
- `channel_ids INT[]` — массив id каналов в шаблоне и расписании. Всегда указываем явно какие боты
- Массив не может быть пустым — рассылка без канала запрещена, валидация на уровне API
- Если Контакт в двух ботах и оба в массиве — получит два сообщения, это нормально
- Дедупликации нет — разные боты, разный контекст

### Логика отписки

- Один Контакт в двух ботах → две записи в `platform_user_channels`
- Отписался от `@margo_forbs_bot` → `is_unsubscribed = true` только для этой записи
- Рассылка через канал → берём только `is_unsubscribed = false` для этого `channel_id`

### Логика рефовода

- Рефовод per-событие: каждое событие с чистого листа, `referrer_participant_id` контекстный
- `first_referrer_id` — только аналитика, никогда не меняется, наград не даёт

## Объединение аккаунтов человека из любого бота — команда /merge (2026-06-15)

**Зачем.** Один человек заходит к организатору с разных площадок (TG, VK, MAX) → у клиента появляется по контакту на каждую (рефералы, регистрации, подарки разбросаны). Команда `/merge` позволяет человеку самому слить их в один профиль из любого бота.

**Как пользоваться (одинаково в TG / VK / MAX):**
1. Узнать свой ID на другой площадке: `/getmyid` в её боте/сообществе (уже работает везде).
2. В текущем боте прислать: `/merge <платформа> <id>` — например `/merge vk 12345678`, `/merge tg 67890`, `/merge max 11111`. Алиасы платформы: tg/telegram, vk/вк, max/макс/мах.
3. Голый `/merge` без аргументов → бот печатает инструкцию.

**Правила слияния (зафиксированы пользователем):**
- **Главный контакт = самый ранний** (меньший `contacts.id` = создан раньше). Не «текущий».
- **Реферер — per-событие**: если оба объединяемых контакта участвуют в ОДНОМ событии и у выжившего (primary) участия реферер пустой, а у secondary заполнен — переносим непустой `referrer_ref_code` на primary-участие. Правило «непустой, иначе от самого раннего» (primary и есть ранний, поэтому его реферер приоритетен, у secondary добираем только если у primary пусто).
- **Область — в рамках одного клиента** (того, в чьём боте человек). client_id: VIP-бот → его клиент; системный бот → системный клиент `system@pluson.ru`.
- **Без кода-подтверждения** — доверяем введённому ID (по решению пользователя). Угнать чужой контакт теоретически можно, зная чужой ID — сознательный trade-off ради простоты.

**Код:**
- Сервис [backend/app/services/contact_merge.py](../backend/app/services/contact_merge.py): `merge_my_account_with_identity` (точка входа из бота) → `find_contact_by_identity` (резолв contact_id по client_id+platform+platform_user_id, учитывает merged_into) → `merge_contacts_oldest_primary` (выбор primary=min(id)) → существующий `merge_contacts`. В `merge_contacts` добавлен шаг переноса реферера на выжившее участие ПЕРЕД удалением secondary-участий — полезен и для ручного мержа в дашборде.
- TG: `/merge` в [backend/bot/handlers/start.py](../backend/bot/handlers/start.py) (`handle_merge`).
- VK: `/merge` в [backend/bot/vk_main.py](../backend/bot/vk_main.py) (`_handle_vk_merge`, вызов в `handle_message_new`).
- MAX: `/merge` + `/getmyid` в [backend/app/api/max_webhook.py](../backend/app/api/max_webhook.py) (`_handle_max_merge`, вызов в `_handle_message_created`). До этого в MAX `/getmyid` не было — добавлен.

**Ответы бота:** `merged` → «✅ Готово! Аккаунты объединены…»; `already` → «уже объединены»; `not_found` → «не нашёл аккаунт {платформа} с ID … у этого организатора».

**Осталось:** E2E на dev/проде (создать 2 контакта разных площадок одному человеку → /merge → проверить что рефералы и участия сложились на ранний контакт).

**⚠️⚠️ Чем задача упирается и почему отложена.**

Бот через Bot API отправляет видео **не больше 50 МБ** — это ограничение самого
Telegram, а не наше. Человек из приложения шлёт до 2 ГБ (4 ГБ с Premium), потому
что приложение заливает файл своим протоколом (MTProto), а бот — через Bot API.
Нарезки выступлений весят сотни мегабайт, то есть **ботом их отправить нельзя**.

Обходной путь — слать **от служебного аккаунта-человека через Telethon**, как в
автонастройке Telegram: там лимит те же 2 ГБ. Решение владельца (2026-09-08):
**брать служебный аккаунт и добавлять его админом в канал**.

⚠️ **Риск, о котором предупреждено до начала работ:** служебный аккаунт
`998700388279` (@margo_co8992) **единственный** и уже занят автонастройкой.
Массовая заливка гигабайтов — типичная причина спам-блока, а спам-блок Telegram
**запрещает и создание ботов** (проверено 07.09.2026: BotFather отвечает
«cannot create new bots»). То есть блокировка на записях **уронит автонастройку
целиком**, и чинится это только новым номером с двухфакторкой, выдержанной 7 дней.

Так владелец уже делал в GetCourse: одна ссылка, одна связка с Zoom, записи под одним ключом создаются РАЗНЫМИ (по эфирам) и потом просто подписываются «день 1», «день 2».
  **Почему сейчас нельзя:** Zoom запоминает данные пользовательской трансляции для встречи — при повторном запуске стартует по старым, ввести другой ключ он не даёт. А у нас ключ СВОЙ У КАЖДОГО ДНЯ: `webinar_rooms.stream_key` под UNIQUE-индексом (`webinar_rooms_stream_key_uq`, миграция 221). Один ключ на три дня база просто не сохранит. Итого: либо три встречи Zoom, либо одна комната на все дни.
  ⚠️ **Кнопку «скопировать ключ во все дни» делать НЕЛЬЗЯ** — выглядит решением, но тихо ломает записи. На ключе держится весь конвейер: склейка берёт куски `WHERE stream_key = $1` без фильтра по дню и времени ([webinar_recording.py](../backend/app/tasks/webinar_recording.py), выборка `chunk_rows`) — запись дня 3 склеилась бы из кусков дней 1+2+3. А `_cleanup_chunks` там же удаляет из хранилища ВСЕ неиспользованные куски ключа — после первого эфира дни 2 и 3 исчезли бы безвозвратно. Плюс `stream_active` встаёт только одной комнате из трёх (вебхук `stream/publish` берёт `fetchrow` по ключу), и HLS-адрес у дней общий — зрители дня 2 увидели бы эфир дня 1.
  **Что делать, когда возьмём в работу (две части, вторая обязательна):**
  1. В настройках дня — «использовать комнату другого дня» / «один эфир на все дни». Комната одна → ключ один → Zoom настраивается однократно, конфликта с UNIQUE нет.
  2. **Починить раскладку записей по эфирам, а не по ключу.** Данные для этого УЖЕ есть: у куска `webinar_recording_chunks.room_id` и `seg_started_at`, у эфира `webinar_sessions.started_at/ended_at` (миграции 321, 224). Выборку для склейки и `_cleanup_chunks` перевести на `room_id` + окно времени сессии. Тогда три дня в одной комнате дадут три отдельные записи — ровно как в GetCourse у владельца.
  ⚠️ Второй пункт нужен и сам по себе: сейчас две параллельные сессии в одной комнате склеятся в один файл, а лишние куски удалятся. Записи эфиров не переснять.
  **Открытый вопрос к владельцу:** записи нужны отдельными файлами по дням или достаточно одной общей на всю конференцию. От ответа зависит объём работы (при «одной общей» второй пункт не нужен).
