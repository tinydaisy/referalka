# TESTING.md — Сценарии тестирования ПЛЮСОН

> Этот файл описывает что и как проверять перед деплоем и после изменений.
> Тесты делятся на: ручные сценарии (end-to-end) и проверки по компонентам.

---

## Приоритет тестирования

**Критично (без этого продукт не работает):**
1. Реферальная цепочка: клик → конверсия → начисление баллов → выдача подарка
2. Регистрация участника через бота
3. Mini App открывается и показывает правильный прогресс

**Важно (ключевые функции):**
4. Клиент создаёт событие и получает ссылку
5. Webhook от GetCourse засчитывает конверсию
6. Рассылка участникам уходит в правильный сегмент

**Дополнительно:**
7. Панель администратора показывает актуальные данные
8. Модуль «Конференция» отображает программу и спикеров

## Сценарий 12 — Тестовое письмо приходит с картинкой (2026-08-14)

Проверять после ЛЮБОЙ правки отправки писем: тест и боевая рассылка обязаны
выглядеть одинаково, иначе клиент проверяет вёрстку, которой в реальной
рассылке нет.

- [ ] Рассылка с фото → «Тест» → в Telegram картинка **и** в письме картинка (не пустое место, не ссылка)
- [ ] Картинка показана **в теле письма**, а не «прикреплением снизу» (Gmail на телефоне — самый строгий: тяжелее ~100 КБ уезжает вниз, поэтому JPEG сжимается до ~90 КБ)
- [ ] Кнопка рассылки есть и в письме (персиковая `#FFCFA4`), не только в боте
- [ ] Рассылка с видео → в письме кликабельная обложка со ссылкой (встроенного плеера в почте не бывает)
- [ ] Заголовок не задвоился: он в теме письма, а не ещё и первой строкой тела
- [ ] То же самое проверить в ОБОИХ разделах — событийные рассылки и общие `/dashboard/broadcasts` (точка теста общая, но проверять обе)

Быстрая проверка доставки на проде: `grep '<message-id>' /var/log/mail.log` → должно быть `status=sent (250 ... OK)`; размер письма в строке `qmgr` показывает, вложена ли картинка (с фото — сотни КБ, без — единицы КБ).

## Известные ограничения (не баги)

- Mini App не работает в обычном браузере — только внутри Telegram
- Проверка подписки на канал работает только если бот является администратором канала
- `points_scope = 'client'` (накопительные баллы across событий) — не реализован в MVP
- **E2E-тест воронки на dev требует отдельного TELEGRAM_BOT_TOKEN от прод-сервера.** Сейчас prod и dev используют один токен @pluson_bot → конфликт getUpdates при одновременном polling. Решение: завести второго бота через @BotFather и положить его токен в dev `.env`, либо тестировать воронку только на prod после деплоя.

## Свой домен клиента (миграция 270)

Раздел: Настройки → «Свой домен». Виден только на тарифе с фичей `custom_domain` (Экстра).

### Домен для страниц

1. Добавить **корневой** домен (`example.ru`) → статус «Ждём DNS», показана запись **A** `@` → `194.156.119.17` (НЕ CNAME — на корне он запрещён стандартом DNS).
2. Добавить **поддомен** (`lp.example.ru`) → показана запись **CNAME** → `pluson.ru`.
3. Домен с чужими записями (свежекупленный обычно висит на парковке регистратора) → кабинет первым шагом перечисляет найденные записи «удалите вот эти». Без их удаления новая запись не сработает.
4. Нажать «Проверить DNS» до настройки записи → отказ с понятным текстом (для корня зовёт ставить A-запись, для поддомена — CNAME), кнопка «Выпустить сертификат» остаётся заблокированной.
5. Прописать запись у регистратора, подождать, снова «Проверить DNS» → «DNS настроен верно», кнопка выпуска разблокирована.
6. «Выпустить сертификат» → статус «Работает», видна дата окончания и остаток дней.
7. Открыть на своём домене: лендинг события `/e/{slug}`, кабинет спикера `/speaker/{slug}`, турнирную таблицу `/t/{slug}/{stage}`, воронку подарка `/m/{slug}`.
8. Открыть на своём домене `/dashboard` → должен увести на `pluson.ru/dashboard` (кабинет живёт только там).
9. Проверить, что ссылки в рассылке ведут на свой домен: сформировать рассылку и посмотреть превью.
10. Отключить домен → страницы на нём перестают открываться, всё возвращается на `pluson.ru`.

## Карточка ссылки события в мессенджере (миграция 503, 2026-09-23)

⚠️ **Мессенджер кеширует карточку.** Проверяя повторно, каждый раз сбрасывайте кеш ботом **@WebpageBot** (отправить ему ссылку) — иначе увидите прошлую версию и решите, что правки не сохранились.

**Настройка**

- Событие → настройки → вниз, к «Публичным ссылкам» → блок «Как выглядит ссылка в мессенджере».
- Поле пустое → в предпросмотре «Приходи {дата} на «{название}»» с настоящей датой и названием.
- Вписать свой текст с `{дата}` и `{название}` → предпросмотр меняется сразу, сохранить → перезагрузить страницу → текст на месте.
- Стереть поле и сохранить → вернулось умолчание (в БД должен лечь `NULL`, а не пустая строка: `SELECT share_preview_text FROM events WHERE id=…`).

**Сама карточка**

- Отправить `pluson.ru/e/{slug}` в Telegram (себе в «Избранное») → под ссылкой афиша события, название и подпись.
- Событие с афишей → в карточке **афиша**, не логотип. Если стоит логотип — проверьте, что афиша вообще загружена и что это не старый кеш.
- Удалить афишу у события → в карточке логотип основателя.
- Ни афиши, ни логотипа → карточка без картинки (не должно быть чужой картинки со страницы).

**Проверить отдельно**

- **Горизонтальная и квадратная афиши вместе** → в карточку идёт горизонтальная, и ровно та же показана в предпросмотре кабинета. Расхождение здесь — главное, что может сломаться (два подзапроса в разных файлах).
- ⚠️⚠️ **ВЕС КАРТИНКИ В КАРТОЧКЕ.** Тяжёлую картинку Telegram молча отбрасывает, и в чате остаётся логотип при верном `og:image` — выглядит как «афиша не подставилась», хотя код исправен. Проверять надо не файл в хранилище, а то, что отдаёт эндпоинт карточки:
  ```
  curl -s "https://pluson.ru/e/<slug>" | grep 'og:image'          # должен вести на /api/v1/share-image/
  curl -sL -o /dev/null -w "%{size_download} байт, %{content_type}\n" \
       "https://pluson.ru/api/v1/share-image/event/<slug>"        # ожидаем сотни КБ, image/jpeg
  ```
  Сам файл афиши в хранилище при этом может оставаться тяжёлым — это нормально, на лендинге нужна чёткая картинка.
- **Тяжёлая афиша (несколько МБ)** → карточка всё равно с афишей: эндпоинт ужимает на лету, пересобирать ничего не нужно.
- **Событие без афиши** → `og:image` ведёт прямо на логотип основателя, а `/api/v1/share-image/event/<slug>` отвечает 404 (так и задумано).
- **Афиша-PNG с прозрачностью** → в карточке фон белый, а не чёрный.
- **Сжатие при сборке** (отдельно от карточки): собрать афишу генератором → файл в хранилище должен весить сотни КБ, а не мегабайты. Проверить все три вида: общие, по дням, индивидуальные (спикерам).
- **Многодневное событие** (конференция с программой на несколько дней) → в подписи ПЕРИОД, а не первый день: «с 24 сентября по 1 октября»; внутри одного месяца — «24–30 сентября».
- **Однодневное с `end_at` вечером того же дня** → период НЕ включается, показывается один день с временем.
- **Событие без даты** («идёт постоянно») → «Приходи на «Название»», без висящего тире и пустого места.
- **Событие только с датой, без времени** → в подписи «26 октября», без «в 00:00».
- **`{дата}` в начале своего текста + событие без даты** → строка не начинается с тире.
- **Все три типа события**: мероприятие, конференция/премия, конкурс — блок на месте, сохраняется.
- **Коллаба** → блока нет вовсе (у неё нет общей публичной ссылки).
- **Описание с HTML** (`<b>`, `<a href>`) → в карточке теги НЕ видны: подпись берётся из своего поля, а не из описания.

### Сценарий 1 — имя бота

- «Каналы» → «Автонастройка» (вкладки нет без фичи `tg_autosetup` — это норма).
- Ввести занятое имя (`test_bot`) → «Проверить» → **«Это имя уже занято»**, кнопка оплаты не активна.
- Ввести свободное → **«Имя свободно»**, кнопка активна.
- Ввести кириллицей / без «bot» на конце → ошибка формата **до** обращения к Telegram.

### Сценарий 2 — оплата и очередь

- ⚠️ Пока `coming_soon=TRUE` кнопки оплаты нет вовсе — это ожидаемо. Для теста: `/admin/tg-setup` → «Услуга» → «Открыть продажу», либо заказ вручную и «Оплачен» в списке заказов.

- Проверить в БД: `bot_token` заполнен, канал появился в `channels` + `client_channels`, `clients.notifications_telegram_chat_id` = id новой группы.

### Сценарий 3 — действия клиента

- Экран показывает две строки: «Зайдите в бота» и «Вступите в группу», обе с кнопками.
- Зайти в бота, нажать «Запустить» → в течение минуты строка становится зелёной, `clients.test_telegram_ids` пополнился вашим id.
- Вступить в группу по ссылке → строка зеленеет, вы админ группы (проверить в Telegram: у вас есть право назначать админов).
- Дождаться передачи бота: `/mybots` в BotFather у ВАС показывает нового бота; сервисный аккаунт из группы вышел.

### Сценарий 4 — канал клиента

- Добавить бота админом в свой канал.
- Проверить: канал появился в «Каналы» → «Чаты для рассылок» без ручного ввода id.

### Сценарий 5 — сгорание

- Заказ с `claim_deadline` в прошлом (правится в БД) → задача `remind` через час: бот удалён, состояние «Сгорело», уведомления ушли.
- Кнопка «Запустить настройку заново — бесплатно» работает **без** повторной оплаты.
- ⚠️ Имя бота при повторе, скорее всего, придётся выбрать другое: удалённый ник BotFather сразу не отдаёт.

### Что проверить отдельно

- **Нет ника Telegram у клиента** → жёлтая плашка, запуск заблокирован.
- **Повторный вебхук оплаты** → `already_paid`, дублей нет.
