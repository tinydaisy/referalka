## 1. Обзор продукта

### 1.1 Суть идеи

**ИИ-Реферальный Сервис** — SaaS-платформа управляемого вирального роста, которая превращает собственную аудиторию Клиента в автоматически работающий канал привлечения новых людей.

Сервис реализует механику **«Партнёрской Игры»**: Участники события получают персональные реферальные ссылки и мотивируются приглашать знакомых через геймификацию, ценностные подарки и психологические триггеры (дофаминовая петля, дефицит, социальное доказательство, соревновательность).

### 1.2 Ключевые отличия от аналогов

| Классические реферальные инструменты | Данный сервис |
|---|---|
| Требуют технических специалистов | Запуск за 15–20 минут без технических знаний |
| Денежные выплаты участникам | Ценностные подарки и геймификация |
| Ручной учёт и управление | Полная автоматизация от клика до бонуса |
| Нет AI | Встроенный AI: анализ, прогнозирование, рекомендации |
| Закупка трафика | Рост за счёт собственной аудитории |

### 1.3 Целевая аудитория (Клиенты сервиса)

**Онлайн-рынок:**
- Эксперты и владельцы онлайн-школ (вебинары, эфиры, Zoom-встречи)
- Продюсеры онлайн-курсов
- Авторские курсы и тематические запуски

**Организаторы событий:**
- Конференции, форумы, бизнес-саммиты
- Нетворкинги, интенсивы, конкурсы, премии
- Любые события с чёткой датой начала

**Офлайн-бизнес и бренды:**
- Офлайн-бизнесы, запускающие промо-акции
- Розничные сети, проводящие промо
- Локальные акции любого масштаба

### 1.4 Проблема и решение

**Проблема:** Стоимость привлечения аудитории растёт, доверие к традиционной рекламе падает, органический охват сокращается. Самый эффективный канал — рекомендация от знакомого — остаётся неуправляемым.

**Решение:** Сервис систематизирует и автоматизирует «сарафанное радио»: превращает аудиторию в управляемый канал привлечения через геймификацию и встроенную психологию поведения.

## 2. Роли и акторы

### 2.1 Клиент
Юридическое или физическое лицо, создающее события на платформе. Работает через **веб-кабинет (браузер)**.

**Возможности:**
- Регистрация и управление профилем
- Создание и настройка Событий
- Управление Партнёрской Игрой (подарки, пороги, материалы)
- Просмотр аналитики и базы контактов
- Управление тарифом/подпиской

### 2.2 Участник
Физическое лицо, участвующее в Событии через реферальную систему. Работает через **Telegram Mini App и Telegram-бот**.

**Возможности:**
- Вход через Telegram (One-Tap Onboarding, без отдельной регистрации)
- Получение персональной реферальной ссылки
- Просмотр своего прогресса, списка подарков
- Шеринг рекламных материалов
- Получение уведомлений о действиях рефералов и начисленных бонусах

### 2.3 Сервис (Автоматика)
Внутренняя бизнес-логика платформы, работающая без участия людей.

**Зоны ответственности:**
- Реферальный движок (учёт переходов и регистраций)
- Выдача персональных ссылок
- Начисление бонусов при достижении порогов
- Антифрод-проверки
- Триггерные уведомления и рассылки
- AI-генерация контента
- Smart Bridge (UTM-проброс, Webhook)
- Публикации в чат события

### 2.4 Администратор
Внутренняя команда платформы. Работает через **панель администрирования**.

**Возможности:**
- Настройка общего Telegram-бота сервиса
- Управление тарифами, пользователями, правами
- Агрегированная статистика по всем Клиентам
- Ревью антифрод-кейсов
- Создание дополнительных администраторов с разными уровнями прав

## 4. Модель данных

Схема БД проектируется сразу под полный функционал всех трёх этапов Roadmap, чтобы исключить миграции при масштабировании.

> **Совместимость с iVision Conf:** схема БД referalka является базой для iVision Conf. Все таблицы ниже переиспользуются без изменений. iVision Conf добавляет поверх конференц-блок (`conferences`, `tracks`, `speakers`, `sessions`, `speaker_applications`). При развёртывании iVision Conf для клиента — схема идентична, в `events` добавляется одна запись конференции.

> **Архитектурное решение (Many-to-Many):** один Telegram-пользователь может участвовать в событиях разных Клиентов. Поэтому личные данные человека и факт его участия в конкретном событии хранятся в **двух отдельных таблицах**. Это исключает дублирование и позволяет Участнику видеть все свои события в едином кабинете Mini App.

### 4.1 Таблица `telegram_users` (Глобальный реестр Telegram-аккаунтов)

Данные, принадлежащие **человеку** — не зависят от конкретного события или клиента.

| Поле | Тип | Описание |
|---|---|---|
| `id` | UUID | Первичный ключ |
| `telegram_id` | BIGINT | Уникальный ID в Telegram (UNIQUE) |
| `telegram_username` | VARCHAR | @никнейм |
| `telegram_avatar_url` | TEXT | URL аватара из Telegram |
| `phone` | VARCHAR | Номер телефона (если получен) |
| `email` | VARCHAR | Email (если оставлен) |
| `first_seen_at` | TIMESTAMP | Дата первого появления в системе |

### 4.1.1 Таблица `event_participants` (Факт участия в событии)

Данные, принадлежащие **конкретному участию** — у одного человека может быть много строк, по одной на каждое событие.

| Поле | Тип | Описание |
|---|---|---|
| `id` | UUID | Первичный ключ |
| `telegram_user_id` | UUID → telegram_users | Кто участвует |
| `event_id` | UUID → events | В каком событии |
| `referrer_participant_id` | UUID → event_participants | Кто пригласил (в рамках этого события) |
| `referrer_chain` | UUID[] | Массив ID предков по цепочке вверх |
| `depth_level` | INTEGER | Уровень вложенности в дереве |
| `status` | ENUM | `interested` / `registered` |
| `is_suspicious` | BOOLEAN | Флаг антифрода |
| `ip_address` | VARCHAR | IP при первом переходе |
| `device_fingerprint` | VARCHAR | Отпечаток устройства |
| `joined_at` | TIMESTAMP | Дата входа в это событие |

> **Пример:** Мария участвует в 3 событиях разных Клиентов — в `telegram_users` одна запись, в `event_participants` три строки. Если Мария сменила @username — обновляем одну запись, а не искать по всем событиям. `referrer_participant_id` ссылается на `event_participants`, а не на `telegram_users` — потому что реферальная связь существует только внутри конкретного события.

| `community_url` | TEXT | Ссылка на чат/комьюнити события |
| `require_subscription` | BOOLEAN | Требовать подписку на канал |
| `subscription_channel_url` | TEXT | Ссылка на Telegram-канал |

## 5. Функциональные требования — Клиент (Web-кабинет)

### 5.1 Раздел «Создание события»

#### 5.1.1 Обязательные поля

| Поле | Тип ввода | Описание |
|---|---|---|
| **Название события** | Текстовое поле | Используется во всех уведомлениях и рассылках |
| **Дата и время** | Date/Time Picker | Включая обязательный выбор часового пояса |
| **Формат** | Dropdown | `Живая встреча` / `Доступ к записи или курсу` / `Бизнес-акция` / `Конференция` |

> **Формат «Конференция»** (Этап 3): при выборе этого формата событие может быть расширено конференц-блоком (программа, спикеры, треки) — через развёртывание iVision Conf на инфраструктуре клиента по отдельному договору.

#### 5.1.2 Необязательные поля

| Поле | Условие отображения | Описание |
|---|---|---|
| Ссылка на лендинг регистрации | Всегда | Если не указана — Участник сразу получает статус «Зарегистрирован» |
| Ссылка на трансляцию | Формат `Живая встреча` | Рассылается в напоминаниях |
| Ссылка на чат/комьюнити | Всегда | Чат для публикации поздравлений |
| Требовать подписку на канал | Переключатель | Проверяется через Telegram API перед выдачей ссылки |

#### 5.1.3 Логика закрытия события

- В момент наступления даты и времени события — сервис автоматически закрывает акцию
- Ссылки прекращают принимать регистрации
- Новым посетителям показывается заглушка: «Акция завершена» + варианты действий (подписаться на канал, перейти в актуальное событие, оставить заявку)

### 5.2 Раздел «Настройка Партнёрской Игры»

#### 5.2.1 Выбор метрики учёта

- **Заинтересовавшиеся** — все, кто перешёл по ссылке и попал в бот
- **Зарегистрировавшиеся** — только прошедшие полную регистрацию

> Сервис всегда ведёт учёт обоих параметров параллельно и отображает обе цифры в аналитике.

#### 5.2.2 Выбор модели реферальной цепочки

- **Одноуровневая** — баллы только за прямые приглашения (MVP)
- **Многоуровневая** — баллы за всю цепочку вглубь без ограничения уровней (Этап 2). Разное количество баллов за тех, кто бесплатный билет приобрел и платный (с лендинга мероприятия с каждого тарифа идет на разые блоки чат-бота (фиксация нужного количества баллов и проверка чтобы дважды регистрации не проходил и не было двойного начисления балов)

#### 5.2.3 Настройка подарков

Для каждого уровня подарка задаётся:

| Параметр | Обязательность | Описание |
|---|---|---|
| Название подарка | Обязательно | Отображается в уведомлениях и кабинете Участника |
| Ссылка на подарок | Обязательно | Отправляется Участнику при достижении порога |
| Порог выдачи | Обязательно | Количество человек для получения подарка |
| Название титула | Необязательно | Например: «Мастер», «Магистр», «Амбассадор» |
| Изображение титула | Необязательно | Шаблон с местом под аватар Участника |
| Лимит выдач | Необязательно | Ограничение числа выдач (создаёт эффект дефицита) |

**Инструменты настройки подарков:**
- Drag-and-drop конструктор уровней
- Готовые пресеты (например, «1-5-10» одним кликом)
- Встроенная памятка со стратегиями («Быстрая победа», «Лестница ценности»)
- AI-анализ логичности прогрессии и предупреждения о перекосах

#### 5.2.4 Дополнительные механики

| Механика | Тип | Описание |
|---|---|---|
| Механика сгорания статуса | Переключатель | Статус «сгорает» через N часов без новых регистраций |
| Специальная акция | Свободный текст | Дополнительный бонус вне основной системы |
| Публикации в чате | Два переключателя | Поздравления о подарках / вовлекающие сообщения |

## 6. Функциональные требования — Участник (Telegram Mini App)

> **Единый кабинет:** Mini App — это приложение сервиса, а не отдельного Клиента. Участник видит все свои события от всех Клиентов в одном интерфейсе. Брендинг каждого события — через афишу и название, загруженные Клиентом. Никаких отдельных Mini App под каждого Клиента нет и не будет.

### 6.1 Онбординг

- **One-Tap Onboarding**: вход в один клик через Telegram без регистрации на сторонних сервисах
- При первом входе — создаётся запись в `telegram_users` (если ещё не существует) и запись в `event_participants` для конкретного события
- Если активирована опция подписки на канал — проверка подписки через Telegram API перед открытием кабинета

### 6.1.1 Экран «Мои события» (главный экран Mini App)

- Список всех событий, в которых участвует данный пользователь (по всем Клиентам)
- Каждая карточка: афиша события, название, дата, статус (активно / завершено), краткий прогресс
- Клик по карточке → переход в детальный кабинет конкретного события

### 6.2 Личный кабинет Участника (внутри одного события)

#### Блок «Мой прогресс»
- Динамическая шкала-«градусник» прогресса до следующего подарка
- Количество зарегистрировавшихся по ссылке
- Список полученных подарков
- Счётчик «Осталось пригласить X человек до подарка N»

#### Блок «Мои подарки»
- Список всех доступных подарков с порогами
- Статус каждого подарка: «Получен» / «Осталось X» / «Заблокирован»
- Если есть лимит — живой счётчик оставшихся мест (обновляется в реальном времени)

#### Блок «Материалы для приглашения»
- Афиша(и) — кнопки «Скачать» и «Поделиться в Story»
- Тексты анонсов — кнопка «Скопировать»
- Персональная реферальная ссылка — кнопки «Скопировать», «Переслать в Telegram», «Поделиться»
- Раздел «Как привлечь больше людей» — мини-уроки по рассылкам

#### Блок «Эффект толпы»
- Бегущая строка с обезличенными уведомлениями о действиях других Участников
- Примеры: «Мария только что получила VIP-гайд», «Алексей стал Мастером»

#### Блок «Специальная акция»
- Отображается если Клиент заполнил поле специальной акции

### 6.3 Получение титулов

- При достижении порога — сервис автоматически подставляет аватар и ник Участника в шаблон
- Формирует изображение-сертификат и отправляет в личное сообщение
- Визуальная насыщенность изображения растёт вместе с уровнем достижения

## 7. Функциональные требования — Сервис (автоматика)

### 7.1 Реферальный движок

- Выдача уникальных персональных реферальных ссылок каждому Участнику
- Учёт переходов (clicks) и регистраций (registrations) раздельно
- Хранение реферального дерева: ID каждого участника, ID родителя, глубина уровня
- При многоуровневой модели — обход дерева вверх по цепочке при начислении баллов

### 7.2 Конфликтный арбитр

**Ситуация:** Участник перешёл по ссылке одного партнёра, а потом по ссылке другого.

**Логика:**
1. Сервис автоматически обнаруживает конфликт
2. Устанавливает `conflict_flag = true` в таблице `referral_events`
3. Уведомляет обе конфликтующие стороны

### 7.3 Автоматическое начисление бонусов

- Сравнивает текущий счётчик Участника с порогами подарков в реальном времени
- При достижении порога — мгновенно отправляет ссылку на подарок в личное сообщение
- Если подарок лимитирован — проверяет `issued_count < limit_count` перед выдачей
- Обновляет счётчик `issued_count` после выдачи

### 7.4 Публикации в чат события

При наличии ссылки на чат и включённых опциях:
- Поздравление с никнеймом Участника, описанием подарка/титула, указанием следующего уровня
- Кнопка «Принять участие в игре» для не присоединившихся
- Сертификат-изображение при получении титула

### 7.5 Механика дедлайна

- При наступлении даты события — автоматически закрывает реферальную механику
- Ссылки переходят в режим «только информационный»
- Новым посетителям — заглушка с альтернативными действиями

### 7.6 Механика сгорания статуса (опция)

- Если включена Клиентом — отслеживает активность каждого Участника
- За 2 часа до сгорания — предупреждение: «Твой статус сгорит через 2 часа»
- В момент сгорания — уведомление + предложение начать заново

## 8. Функциональные требования — Администратор

### 8.1 Панель управления

- Настройка общего Telegram-бота сервиса: приветствия, системные сообщения, внешний вид
- Управление тарифами: создание, редактирование, деактивация
- Управление Клиентами: просмотр, статус, ручные изменения
- Управление правами: создание дополнительных администраторов с ограниченными правами

### 8.2 Агрегированная статистика

- Количество зарегистрированных Клиентов
- Количество активных/завершённых событий
- Суммарное количество Участников по каждому Клиенту
- Количество выданных подарков

### 8.3 Антифрод-панель

- Полный лог подозрительных активностей
- По каждому флагу: причина, данные аккаунта, временная метка, рекомендуемое действие
- Кнопки «Подтвердить блокировку» / «Снять блокировку»

## 9. Smart Bridge — интеграционный модуль

### 9.1 Принцип работы

```
Участник → [переходит по реф. ссылке] → Smart Bridge добавляет UTM-параметры
→ Лендинг Клиента → Участник регистрируется → Лендинг отправляет Webhook
→ Smart Bridge принимает Webhook → Регистрация засчитывается в сервисе
```

### 9.2 UTM-проброс

- К каждому URL лендинга автоматически добавляется реферальный код как UTM-параметр
- Параметр сохраняется в куки/localStorage для корректного отслеживания

### 9.3 Webhook-обработчик

- Принимает POST-запрос от внешней платформы при регистрации
- Находит Участника по реферальному коду
- Обновляет статус с `interested` → `registered`
- Запускает начисление бонусов и уведомления

### 9.4 Поддерживаемые платформы

| Платформа | Статус |
|---|---|
| GetCourse | MVP |
| Tilda | MVP |
| WordPress / WooCommerce | MVP |
| Самописные сайты (универсальный Webhook) | MVP |
| AmoCRM, Bitrix24, GA, Meta Pixel | Этап 3 |

### 9.5 Ручной режим

Если интеграция для платформы недоступна — предусмотрен ручной режим подтверждения регистрации через бот.

## 10. AI-модуль

### 10.1 AI-копирайтер

Генерирует 3 варианта текста для каждого из типов:

| Тип | Формат | Варианты |
|---|---|---|
| Анонс/пост в соцсети | Разная длина и тональность | Дружеский / Экспертный / Интригующий |
| Текст для личных рассылок | Разговорный язык | 3 варианта |
| Текст для Stories | Короткий, оптимизированный по длине | 3 варианта |

**Вход:** название события, описание, формат, дата
**Выход:** тексты в кабинете Клиента → Клиент выбирает → тексты отображаются у Участника

### 10.2 AI-генератор афиш

- Генерирует визуальный рекламный макет на основе данных события
- Автоматически подставляет: название, дату и время, ключевую выгоду
- Дополнительно генерирует версию под Stories (9:16)
- Клиент может нажать «Перегенерировать» для нового варианта

### 10.3 Конструктор сертификатов/титулов

- Клиент загружает шаблон с местом под аватар
- Сервис автоматически подставляет круглый аватар и ник Участника
- Формирует готовое изображение и отправляет Участнику

### 10.4 AI-поведенческий анализатор

Анализирует в фоне:
- Скорость прироста регистраций
- Часы пиковой активности
- Процент Участников, остановившихся на каждом уровне подарков

**Вывод — карточки-рекомендации для Клиента:**
- «Рекомендуем снизить порог для подарка №2 — 62% участников останавливаются на этом шаге»
- «Пик регистраций прогнозируется в четверг-пятницу — рекомендуем рассылку в среду вечером»

Клиент может применить рекомендацию в один клик или проигнорировать.

### 10.5 Встроенный советник при создании события

- AI анализирует названия подарков и предупреждает о «сухих» формулировках
- Показывает прогноз конверсии: при каком пороге первого подарка выше вероятность активного участия
- Подсвечивает рекомендуемый минимальный порог

## 11. Антифрод-модуль

Работает автоматически в фоне без участия Клиента или Администратора.

### 11.1 Защита от мультиаккаунтов

**Признаки мультиаккаунтинга:**
- Одинаковый номер телефона Telegram
- Совпадающие IP-адреса при регистрации
- Идентичное время действий и последовательность шагов (поведенческий паттерн)

**Реакция:** временная блокировка начисления баллов + уведомление Администратора

### 11.2 Проверка IP-адресов

- Фиксируется IP при каждом переходе и регистрации
- Несколько регистраций с одного IP в короткий промежуток — помечаются как подозрительные
- Пометка «Подозрительная активность» отображается в базе контактов Клиента

### 11.3 Анализ поведенческих паттернов (AI)

- AI анализирует скорость прохождения шагов, паузы, последовательность переходов
- Аномально быстрое или механическое поведение (боты) — помечается флагом

### 11.4 Блокировка саморефералов

- Автоматически блокирует переход по собственной реферальной ссылке
- Баллы не начисляются
- Участнику отправляется уведомление: «Самоприглашение не засчитывается»

### 11.5 Блокировка подозрительных цепочек

**Признаки аномальной цепочки:**
- 10+ последовательных аккаунтов с одного устройства
- Все аккаунты без фото профиля и без истории в Telegram

**Реакция:** приостановка начислений + уведомление Администратора для ручной проверки

## 12. Система уведомлений

### 12.1 Мгновенные уведомления

| Триггер | Текст уведомления |
|---|---|
| Новый реферал перешёл по ссылке | «Твой друг заинтересовался! Тебе +1 к прогрессу» |
| Новый реферал зарегистрировался | «Твой друг зарегистрировался! До подарка №N [название] — ещё X человек» |
| Приближение к порогу | «Осталось всего 1 приглашение до подарка №2!» |
| Получение подарка | Описание подарка + следующий доступный + сколько осталось |
| Конфликт реферальных ссылок | «По твоей ссылке и ссылке другого партнёра перешёл один человек. Мы уведомили обе стороны» |

> Уведомление о регистрации содержит динамический расчёт: сервис берёт текущий счётчик, вычитает из порогов и подставляет остаток. Полученные подарки из сообщения исключаются.

### 12.2 Рассылки-напоминания о событии

| Срок до события | Содержание |
|---|---|
| За 3 дня | Напоминание + ссылка на трансляцию + мотивация |
| За 1 день | Напоминание + ссылка + призыв поделиться |
| За 30 минут | «Скоро начинаем!» + ссылка |
| За 5 минут | «Уже начинаем!» + ссылка |

### 12.3 Вовлекающие рассылки (отдельная линия)

Не дублируют напоминания о событии. Включают:
- Напоминание о персональной реферальной ссылке
- Текущий прогресс и сколько осталось до следующего подарка
- Социальное доказательство: «Другие участники уже получают призы»

Частота подбирается автоматически с учётом активности Участника и дней до события.

### 12.4 Ежесуточный дайджест

«Сегодня 15 человек получили титул Магистра. Ты в 5 шагах от них!»

Тексты ротируются (антиспам).

### 12.5 Антиспам-система

- Все уведомления одного типа ротируются по вариантам текста
- Индекс варианта сохраняется в `notifications_log.text_variant`
- Исключает привыкание к однотипным сообщениям

## 13. Монетизация и тарифная модель

### 13.0 Стратегия монетизации по этапам

**Этап 1 (MVP) — без paywall:**
Все клиенты MVP получают бесплатный «Beta»-доступ ко всему функционалу MVP. Платёжная система не подключается. Цель — протестировать механику с реальными пользователями и получить обратную связь до введения ограничений.

**Что закладывается в код с первого дня (даже без paywall):**
- Таблица `tariffs` существует в БД
- Каждый клиент привязан к тарифу через `tariff_id` (в MVP — тариф «beta»)
- Middleware проверки лимитов написан, но для «beta»-тарифа возвращает разрешение на всё

**Этап 2 — включение paywall:**
После получения первых реальных отзывов и понимания что работает — проектируются финансовая модель, точные цены и подключается платёжная система (ЮKassa или Stripe). Тарифная сетка финализируется на основе реального использования, а не предположений.

**Этап 3 — расширение монетизации:**
Дополнительные платные опции: увеличенный лимит базы, дополнительные AI-генерации, индивидуальный онбординг, приоритетная поддержка.

### 13.1 Тарифные планы

### 13.2 Источники дохода

1. Ежемесячные и ежегодные подписки на тарифные планы
2. Апсейл при достижении лимитов тарифа
3. В перспективе: дополнительные платные опции (увеличенный лимит базы, дополнительные AI-генерации, индивидуальный онбординг)

### 13.3 Юнит-экономика

**Структура расходов:**
- Серверная инфраструктура (масштабируется с нагрузкой, но медленнее дохода)
- AI-генерации (стоимость API, ограничивается лимитами тарифа)
- Разработка и поддержка продукта
- Поддержка клиентов

**Логика масштабирования:** платформенная модель — фиксированные затраты делятся на всё большее число Клиентов. Маржинальность каждого нового Клиента выше предыдущего.

## 14. Нефункциональные требования

### 14.1 Производительность

- Готовность к **5 000+ одновременных регистраций** без деградации скорости
- Время отклика личного кабинета Участника — не более 500 мс
- Время отправки уведомлений после события — не более 1 секунды

### 14.2 Масштабируемость

- Горизонтальное шардирование БД для хранения реферальных деревьев
- Асинхронные очереди обработки событий (регистраций, переходов, начислений)
- Кэширование часто запрашиваемых данных (счётчики, прогресс, личный кабинет)
- CDN для медиа-контента (афиши, сертификаты)

### 14.3 Надёжность

- Автоматическое резервирование данных
- Автоматическое восстановление при сбоях
- Мониторинг нагрузки в реальном времени с алертами

### 14.4 Безопасность

- Проверка подписки на Telegram-канал через официальный Telegram API
- Защита Webhook-эндпоинтов (подпись запросов)
- IP-логирование для антифрода

### 14.5 Расширяемость

- Схема БД рассчитана на все этапы Roadmap без миграций
- Поле `is_ai_generated` в `promo_materials` позволяет добавить AI без изменения структуры
- Поле `referral_mode` в `events` позволяет включить многоуровневую модель через интерфейс

## 15. Дорожная карта (Roadmap)

### Этап 1 — MVP

**Цель:** рабочая версия, решающая основную задачу Клиента — автоматическое управление реферальной кампанией.

**Включает:**
- Создание и настройка событий через Web-кабинет (все поля из Раздела 5.1)
- Одноуровневая реферальная модель
- Фиксированные 3 подарка с порогами 1 / 5 / 10 (настраиваемые через интерфейс в Этапе 2)
- Smart Bridge (Webhook-поддержка для GetCourse, Tilda, WordPress, самописных сайтов)
- Telegram Mini App: личный кабинет, прогресс, реферальная ссылка, раздел материалов (ручная загрузка)
- Мгновенные уведомления (переход, регистрация, приближение к порогу)
- Напоминания о событии (за 3 дня, 1 день, 30 мин, 5 мин)
- Выдача подарков и фиксация конфликтов
- Базовая аналитика: переходы, регистрации, плоская таблица рефералов
- Панель Администратора: Клиенты, активные события, суммарное число Участников

**Архитектурный принцип MVP:** БД проектируется сразу под полный функционал — без переписывания схемы при переходе к следующим этапам.

---

### Этап 2 — Рост и автоматизация

**Цель:** добавить AI-функции и полноценную многоуровневую модель.

**Включает:**
- AI-модуль: копирайтер (посты, рассылки, Stories), генератор афиш под Stories
- Многоуровневая реферальная модель + визуальное дерево в кабинете Клиента
- Гибкая настройка числа подарков и порогов (N подарков, любые пороги)
- Конструктор сертификатов/титулов с автоподстановкой аватара
- Расширенная аналитика: конверсия, скорость роста, топ-участники, тепловая карта
- Механика сгорания статуса
- Лимитированные подарки с живым счётчиком
- AI-поведенческий анализ и рекомендации по порогам

---

### Этап 3 — Enterprise и масштабирование

**Цель:** работа с крупными Клиентами, высокими нагрузками, корпоративными требованиями.

**Включает:**
- High-Load инфраструктура: асинхронные очереди, CDN, горизонтальное масштабирование, резервирование
- Полноценный антифрод-модуль: IP-анализ, поведенческий паттерн, мультиаккаунты
- Расширение Smart Bridge: AmoCRM, Bitrix24, Google Analytics, Meta Pixel
- Маркировка рекламных материалов согласно законодательству
- Открытый API для сторонних разработчиков

## 16. Позиционирование

**Слоган:** «Управляемое сарафанное радио»

**Ключевое утверждение:** Это не реферальный бот. Это не простая реферальная программа. Это архитектура управляемого вирусного роста — SaaS-платформа, которая превращает вашу аудиторию в канал привлечения, автоматически управляет этим каналом и усиливает его с помощью искусственного интеллекта.

**Целевое позиционирование:** инструмент для тех, кто хочет расти без рекламных бюджетов — через силу своей собственной аудитории.

**Ключевые дифференциаторы:**

| # | Дифференциатор |
|---|---|
| 1 | Запуск за 15–20 минут без технических специалистов |
| 2 | Мотивация через ценностные подарки, не денежные выплаты |
| 3 | Полная автоматизация цикла от выдачи ссылки до начисления бонуса |
| 4 | Встроенный AI как рабочий инструмент: анализирует, прогнозирует, рекомендует |
| 5 | Психология вшита в продукт: дофаминовая петля, дефицит, социальное доказательство, соревновательность |
