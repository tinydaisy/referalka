# Система тикетов техподдержки ПЛЮСОНа — план

> Статус: **план, код не написан**. Дата: 2026-08-05.
> Поддержка КЛИЕНТОВ платформы (не участников событий).

---

## 1. Зачем и что не так сейчас

Клиент ПЛЮСОНа задаёт вопрос — и вопрос теряется. Сегодня:

- клиент пишет в @pluson_bot (`?start=question`) → сообщение ложится в `direct_messages` клиента 3 и улетает уведомлением `#user_message` в канал;
- часть клиентов пишет напрямую в личку @margo_forbs (ссылки разбросаны по 9 страницам `/dashboard/help/*`) — эти обращения **не попадают в платформу вообще**;
- бот отвечает «Спасибо, скоро вам ответим 💛» — обещание ничем не подкреплено: нет очереди, нет ответственного, нет статуса;
- нельзя ответить на вопросы: сколько сейчас открытых, кто их ведёт, что висит третий день, на что вообще не ответили.

Переписка есть. **Учёта работы нет.**

Тикет — это не переписка, а карточка задачи поверх переписки:

| | Диалог (есть сейчас) | Тикет |
|---|---|---|
| Живёт | вечно, одной лентой | от вопроса до закрытия |
| Кто отвечает | кто первый увидел | назначенный человек |
| Когда «всё» | никогда | статус «закрыт» |
| Видно | «есть непрочитанные» | «5 в работе, 2 ждут ответа, 1 висит 3 дня» |

## 2. Три точки входа, один тикет

Референс — Reg.ru: заявка одна, каналов несколько.

| Точка входа | Кто | Что происходит |
|---|---|---|
| **Кабинет → Тех.поддержка → «Мои заявки»** | клиент ПЛЮСОНа | видит свои обращения, статусы, переписку; кнопка «Написать заявку» |
| **@pluson_bot** (Telegram) | клиент ПЛЮСОНа | пишет свободно → тикет создаётся сам |
| **MAX-бот ПЛЮСОНа** | клиент ПЛЮСОНа | то же ⚠️ требует подключения бота, см. §8 |
| **/admin/tickets** | Марго + менеджеры | вся очередь: взять, ответить, закрыть |

Клиент начал в боте — продолжил в кабинете. Это **один тикет**. Ответ менеджера уходит туда, откуда пришёл вопрос (в бот — сообщением, в кабинет — в ленту).

## 3. ⚠️ Главная сложность: чей это клиент?

Человек пишет в бота. Знаем `tg_id` и ник. В базе клиента 3 создаётся `contacts` + `platform_users`. Но **связи с записью в `clients`** (кабинет, тариф, подписка) нет — она есть только через `contacts.linked_client_id`, которое заполняется вручную командой `/pluson_connect` и потому почти всегда пусто.

Решение — три слоя, от надёжного к запасному.

### Слой 1 — детерминированная привязка (основной путь)

Кнопка в кабинете ведёт не на `?start=question`, а на **`?start=q_<подписанный_токен>`**, где зашит `client_id`. Клиент залогинен — мы точно знаем, кто он.

⚠️ Механизм подписанных токенов **уже написан**: `backend/app/services/pluson_connect_token.py` + `backend/app/api/pluson_connect.py`. Переиспользовать, не изобретать.

Побочный эффект: заодно проставляется `contacts.linked_client_id` → все последующие сообщения этого человека узнаются сами, уже без токена.

### Слой 2 — автосопоставление (кто пришёл мимо кнопки)

По очереди:
1. `platform_users.username` ↔ `clients.telegram_username` (регистронезависимо, `@` отбрасываем)
2. `contacts.email_normalized` ↔ `clients.email`
3. `contacts.phone_normalized` ↔ `clients.phone`

Нашли **ровно одного** — привязываем (`contacts.linked_client_id`) и помечаем тикет `client_match='auto'`.
Нашли несколько или ноль — **не гадаем**, оставляем неопознанным.

### Слой 3 — ручная привязка менеджером

В карточке тикета поле «Клиент» с поиском. Менеджер выбирает за две секунды, связь запоминается навсегда (`client_match='manual'`).

### Принцип

**Тикет создаётся ВСЕГДА, даже если клиент не опознан.** Неопознанный — обычный тикет с пометкой «клиент не определён», а не потерянное сообщение. Так работает GetCourse: обращение есть всегда, привязка дозревает позже.

## 4. Статусы

Короткая цепочка, больше не нужно:

```
Новый  →  В работе  →  Ждёт ответа клиента  →  Закрыт
  ↑                                              │
  └──────────── клиент написал снова ────────────┘
```

- **`new`** — никто не взял. Висит в общей очереди, видят все менеджеры.
- **`in_progress`** — менеджер взял на себя (`assigned_admin_id`). У остальных пропадает из «Свободных».
- **`waiting_client`** — менеджер ответил, ждём реакцию. Важный статус: тикет не «висит на нас».
- **`closed`** — вопрос решён.

**Автопереходы:**
- клиент написал в тикет со статусом `waiting_client` → обратно в `in_progress` (ответственный сохраняется);
- клиент написал в `closed` → **переоткрытие** в `new` (или `in_progress`, если ответственный ещё работает);
- `waiting_client` без ответа 3 суток → автозакрытие (Celery beat, раз в сутки).

⚠️ Кнопка **«Взять»** — защита от двух ответов на один вопрос. Пока `assigned_admin_id IS NULL`, тикет ничей.

## 5. Схема БД

### `support_tickets`

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | BIGSERIAL PK | |
| `number` | TEXT UNIQUE | человекочитаемый номер для клиента (напр. `2026080500123`) |
| `contact_id` | INT → contacts SET NULL | кто написал (контакт в базе клиента 3) |
| `client_id` | INT → clients SET NULL | **какой клиент платформы** — может быть NULL (не опознан) |
| `client_match` | TEXT | `token` \| `auto` \| `manual` \| NULL — как привязали (для отладки качества) |
| `subject` | TEXT | тема; из первого сообщения (первые ~80 символов) или задана клиентом в форме |
| `status` | TEXT | `new` \| `in_progress` \| `waiting_client` \| `closed` (CHECK) |
| `priority` | TEXT | `normal` \| `high` (CHECK), default `normal` |
| `source` | TEXT | `telegram` \| `max` \| `web` — откуда пришёл |
| `assigned_admin_id` | INT → admins SET NULL | кто взял |
| `assigned_at` | TIMESTAMPTZ | когда взял |
| `first_response_at` | TIMESTAMPTZ | первый ответ менеджера (метрика скорости) |
| `last_message_at` | TIMESTAMPTZ | последнее сообщение в тикете (сортировка очереди) |
| `closed_at` | TIMESTAMPTZ | |
| `closed_by_admin_id` | INT → admins SET NULL | |
| `created_at`, `updated_at` | TIMESTAMPTZ | |

Индексы: `(status, last_message_at DESC)` — очередь; `(assigned_admin_id, status)` — «мои»; `(client_id)`; `(contact_id)`.

### `support_ticket_messages`

⚠️ **Сообщения храним отдельно, а НЕ ссылкой на `direct_messages`.**

Причина: `backend/app/tasks/dialog_retention.py` удаляет `direct_messages` старше **365 дней** (`RETENTION_DAYS = 28`-я строка). Тикет с историей переживёт этот срок — ссылки протухнут. Дублирование текста здесь оправдано.

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | BIGSERIAL PK | |
| `ticket_id` | BIGINT → support_tickets CASCADE | |
| `author_kind` | TEXT | `client` \| `agent` \| `system` (CHECK) |
| `author_admin_id` | INT → admins SET NULL | кто из менеджеров написал |
| `text` | TEXT | |
| `media_url`, `media_kind` | TEXT | вложения (в R2, как в диалогах) |
| `source` | TEXT | `telegram` \| `max` \| `web` |
| `direct_message_id` | BIGINT NULL | ссылка на `direct_messages` (для сверки, необязательная) |
| `is_internal` | BOOL default FALSE | **внутренняя заметка** — видит только поддержка, клиенту не уходит |
| `created_at` | TIMESTAMPTZ | |

Индекс: `(ticket_id, created_at)`.

### Роль менеджера в `admins`

Новая колонка **`admins.role`** TEXT default `'admin'`, CHECK `('admin','support')`.

- `admin` — как сейчас, полный доступ;
- `support` — **видит только `/admin/tickets`**, ничего больше.

⚠️ Существующий флаг `is_superadmin` не трогаем — он проверяется ровно в одном месте (`backend/app/api/admin.py:735`, гейт создания админов) и на фронте не используется вовсе.

⚠️ `get_current_admin` (`backend/app/auth.py:49-57`) возвращает **сырой JWT-payload и в БД не ходит** — роль надо либо класть в токен при логине, либо читать из БД в гварде (как сделано с `get_grant_access_level` для помощников — там читают из БД, чтобы смена прав применялась без перелогина; здесь лучше так же).

## 8. ⚠️ MAX-бот: почему не принимает и что нужно

**Системность канала здесь ни при чём** — у клиента 3 и Telegram системный (`channels.id=7`, `is_system=TRUE`), и он отлично работает. Дело в способе приёма.

| | Telegram (`channels.id=7`) | MAX (мигр. `090_system_max_channel.sql:14-30`) |
|---|---|---|
| `is_system` | TRUE | TRUE |
| `bot_token` в БД | **заполнен** (рабочий) | **пустой `''`** |
| Приём | **polling** из `.env` (`backend/bot/main.py`) — резолв по БД не нужен | **webhook** по `sha256(token)[:32]` |
| Итог | работает | `unknown secret` → 404 |

Причина ровно в двух местах:
1. `bot_token=''` в БД (мигр. 090 комментарий стр. 7-8: реальный токен только в `.env`);
2. `backend/app/api/max_webhook.py:88-116` — `_resolve_token_by_secret` перебирает **только `is_system=FALSE`** каналы с непустым токеном. Системный не проходит по обоим признакам.

⚠️ `backend/app/api/referrals.py:80-87` фиксирует то же: «бот фактически не заведён: вебхук не резолвится (`unknown secret` → 404), отвечать нечем».

**Что нужно сделать (данные + маленькая правка, не переписывание):**
1. записать реальный токен MAX-бота в `channels.bot_token` этого канала;
2. снять запрет на системный канал в резолве вебхука — либо разрешить `is_system=TRUE` в `_resolve_token_by_secret`, либо перевести MAX-канал клиента 3 в `is_system=FALSE`;
3. убедиться, что привязка в `client_channels` для клиента 3 активна (`is_active=TRUE`) — сейчас мигр. 090 ставит `FALSE`;
4. зарегистрировать webhook-URL в настройках MAX-бота.

⚠️ **Токен не хранить в git и не пересылать в переписке.** Присланный в чат токен — перевыпустить в MAX.

⚠️ Второй нюанс: `backend/app/api/max_webhook.py:661` — весь архив и уведомление обёрнуты в `if client_id_override:`. Если `client_id` не резолвится, сообщение **не сохраняется вообще**. При врезке тикетов это надо учесть.

## 9. Этапы

**Этап 1 — ядро (минимум, который уже полезен)**
1. Миграция: `support_tickets`, `support_ticket_messages`, `admins.role`.
2. Сервис `support_tickets.py`: создать/дописать тикет, резолв клиента (3 слоя), автопереходы статусов.
3. Врезка в TG: `handle_user_message` + `handle_user_media` → тикет.
4. Токен привязки в `?start=q_<token>`.
5. `/admin/tickets`: очередь, карточка, «Взять» / ответить / «Закрыть».
6. Роль `support` + гвард.

**Этап 2 — портал клиента**
7. `/dashboard/help/tickets` — «Мои заявки», список + карточка + «Написать заявку».
8. Замена пункта сайдбара.
9. Уведомление клиенту в бот при ответе менеджера.

**Этап 3 — MAX и автоматика**
10. Подключение MAX-бота клиенту 3 (настройка) + врезка в `max_webhook`.
11. Автозакрытие `waiting_client` через 3 суток (Celery beat).
12. Уведомление поддержке о новом тикете (`notify_organizer_all_channels`, `kind='support'`).

**Этап 4 — качество (потом)**
13. Внутренние заметки, приоритет, метрика скорости первого ответа.
14. Шаблоны быстрых ответов.
15. Замена ссылок на личку @margo_forbs в `/dashboard/help/*` на создание тикета.
