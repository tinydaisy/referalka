## Найденная причина

MediaMTX v1.19 требует от плеера **cookie-сессию**:

```
GET /live/{key}/index.m3u8       → 302 + Set-Cookie: hlsSession=...
GET /live/{key}/main_stream.m3u8 → 401 «authentication error»   (без cookie)
```

Проверено: **401 стабильно, 5 запросов из 5.**

⚠️ **Поток при этом исправен:** `recording 2 tracks (H264, MPEG-4 Audio)`, запись пишется, муксер поднят. `ffprobe` по свежему сегменту — `h264` + `aac`, звук есть.

**Почему только Safari:** он играет HLS **нативно** (`<video src>`), cookie уходит сама и CORS его не касается. Все остальные идут через **hls.js → XHR**, а XHR cookie по умолчанию не посылает.

⚠️⚠️ **Ключевая деталь (найдена последней):** MediaMTX отдаёт cookie ДВАЖДЫ, второй раз с `Partitioned`:

```
set-cookie: cookieCheck=1
set-cookie: cookieCheck=1; HttpOnly; Secure; SameSite=None; Partitioned
```

`Partitioned` (CHIPS) — вот почему одного `withCredentials` не хватило для Chrome/Яндекса.

## Что пробовали: что именно и с каким результатом

| № | Правка | Результат | Действует? |
|---|---|---|---|
| 1 | Убрать дублирующий `add_header Access-Control-Allow-Origin "*"` из `location /live/`, `/hls/` | Нужна, но недостаточна | **ДА** |
| 2 | `xhrSetup: xhr.withCredentials = true` в hls.js | Safari + Chrome + MI пошли; **Яндекс нет** | **ДА** |
| 3 | `hlsTrustedProxies: [127.0.0.1/32]` | `child=401` — без изменений | нет, откачено |
| 4 | `hlsCDNSecret: ""` | `child=401` — без изменений | нет, откачено |
| 5 | `hlsDirectory` + `root` в nginx (отдача файлами) | **ПОЛОЖИЛО ВСЁ, включая Safari** | нет, откачено |
| 6 | `playerLoading` стартует в `true` (крутилка сразу) | Убрало «чёрный экран без кнопки» | **ДА** |

### Почему №1 нужна

MediaMTX сам отдаёт CORS с конкретным origin + `Allow-Credentials: true`. Наш `add_header` приходил ВТОРЫМ — браузер отбрасывает ответ с двумя разными CORS-заголовками, а с cookie значение `*` запрещено стандартом. ⚠️ Вернуть = снова чёрный экран, даже с №2.

### Почему №5 всё положило (главный урок)

`hlsDirectory` **затёрся при откате `mediamtx.yml` из бэкапа**. MediaMTX перестал писать сегменты, а СТАРЫЕ плейлисты остались лежать на диске. nginx отдавал их с кодом **200**, плеер шёл за сегментами → **404**.

```
04:50:03  main_stream.m3u8            200  761      ← плейлист есть
04:50:03  6335cde59c4d_main_seg194.ts 404  564      ← а сегмента нет
```

⚠️⚠️ **У схемы ДВЕ части** (`root` в nginx + `hlsDirectory` в mediamtx.yml). Отвалилась вторая — первая **не падает, а отдаёт мусор с кодом 200**: ломается МОЛЧА и в опасную сторону. Проксирование так деградировать не может.

**Если возвращаться к №5** — только вне эфира и обязательно проверив, что сегменты РЕАЛЬНО пишутся:

```bash
find /var/www/plusson/media-server/hlsout -name '*.ts' | wc -l   # должно быть > 0
```

Наличия `.m3u8` НЕДОСТАТОЧНО — именно на этом и погорели.

## Что осталось сделать (ВНЕ эфира)

1. **Довести №5 до конца** — `hlsDirectory` + проверка `.ts > 0` + переключение nginx. Тогда cookie не нужна вовсе и разница между браузерами исчезает. Это лечение причины, а не симптома.
2. ⚠️ Разделять код по браузерам (запрос владельца) — **не рекомендую**: выбор всего один (нативный HLS для Safari / hls.js для остальных), а ветки под Chrome-iOS, Яндекс-iOS, Chrome-Android, MI пришлось бы вечно поддерживать, и каждая может отвалиться молча. №1 убирает саму причину и работает везде одинаково.
3. ⚠️ Отдельная болезнь, НЕ путать с cookie: `WAR segment duration changed from 2s to 4s` — нестабильный keyframe **у кодировщика**, рывки на iOS. Лечится в Zoom/OBS (интервал 2 с), не в коде.
