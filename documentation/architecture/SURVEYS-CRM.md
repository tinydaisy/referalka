### Дашборд аналитики — квадратики-разрезы с пересечением (миграция 284 от 2026-08-13, ПРОД)

Свои срезы базы вместо выгрузок в Excel. **Квадратик = РАЗРЕЗ** (по какому полю строятся полоски) **+ УСЛОВИЯ** (кого вообще считаем). Пример владельца: разрез «Рассматривает работу с наставником» + условие «доход из вилок от 200 тысяч» — сразу видно, кто из платёжеспособных готов покупать. Гейт — фича **`analytics_dashboard`** (Экстра/vip + admin).

Два входа, **движок один**: раздел «Аналитика» → подвкладка «Дашборд» (по всей базе) и карточка события → «Отслеживания» → «Дашборд» (бэк молча добавляет условие «контакт — участник этого события»). Компонент один — [DashboardView.tsx](web/src/components/analytics/DashboardView.tsx), отличается только пропом `eventId`.

**⚠️ Дашбордов МНОГО** — «Портрет базы», «Кто готов покупать» и т.д. Никаких UNIQUE на `(client_id)`: это список, а не единственная запись на клиента.

#### ⚠️ Разрез бывает ДВУХ происхождений — оба обязательны

| Источник | Значения лежат | Ключ |
|---|---|---|
| Поле контакта (`contact_fields`) | `contact_field_values` (1 строка на контакт+поле) | `field:3` |
| Вопрос анкеты (`survey_questions`) | `survey_answers` → `survey_responses.contact_id` | `question:24` |

**У клиента 1 на проде у ВСЕХ вопросов анкет `field_id IS NULL`** — то есть «Рассматривает наставника» физически НЕ в `contact_field_values`. Поддержать только `contact_fields` (как звучит ТЗ буквально) значило бы потерять ровно то, что просили пересекать. Оба источника сводятся к `contact_id`, поэтому пересекаются свободно — единая точка `_value_expr` в [analytics_cards.py](backend/app/services/analytics_cards.py). **При новом источнике разрезов — добавлять туда, а не писать свой SELECT.**

#### ⚠️ Три грабли, проверенные на живых данных

**1. `jsonb_array_elements_text` нельзя внутри `CASE`** — Postgres: «set-returning functions are not allowed in CASE». В `survey_analytics` приём работает только потому, что там он в `CROSS JOIN LATERAL`. У нас разворот идёт через `UNION ALL`: ветка «массив» + ветка «не массив».

**2. Мультиселект обязан разворачиваться.** `value` хранит варианты СКЛЕЕННЫМИ через запятую («Творчество, Заработок»). Точное совпадение по «Эксперт/консультант» даёт **426** человек, с разворотом — **684**: 258 потерянных, у кого выбрано несколько статусов сразу. Без разворота каждая КОМБИНАЦИЯ ответов стала бы отдельной полоской.

**3. `value_json` НЕконсистентен — источник истины `value` (TEXT).** Анкета пишет туда настоящий тип (число `50000`), а ручная правка в карточке (`PUT /contacts/{id}/fields`) — всегда строку. Числа приводим из `value` через `NULLIF(regexp_replace(...),'')::numeric` с охраной `value ~ '^-?[0-9]+...'`.

#### ⚠️ Операторы — ПО ТИПУ поля, иначе бессмыслица

«Уровень дохода» у клиента — **`select` с вилками** («200.000- 300.000 рублей»), а не число. Сравнений `>` `<` там нет в принципе: «больше 200 тысяч» = отметить галочками нужные вилки (оператор `in`). Матрица — `OPERATORS_BY_KIND`: число/шкала → `= ≠ > < >= <=`, список → `= ≠ один из`, да/нет → Да/Нет, всем → «заполнено / не заполнено».

#### ⚠️ Знаменатель процентов — ОТВЕТИВШИЕ, а не все прошедшие условия

Процент считается от тех, кто прошёл фильтры **и заполнил сам разрез** (`answered`), а не от всех прошедших фильтры (`scope`). Молчащий человек не «против» — он неизвестен, и тянуть долю вниз не должен. Тот же принцип, что в аналитике анкет. На карточке показываются обе цифры («ответили 80 из 120») — иначе не видно полноту разреза.

#### ⚠️ Два вида квадратика — «плитка» и «список» (миграция 285)

**«Квадратик» в понимании владельца — ПЛИТКА С ОДНОЙ ЦИФРОЙ** («200-300 т.р. — 176 пользователей»), как в дашбордах GetCourse, откуда клиент уходит. Первая версия делала только карточку со списком всех вариантов — это другое. `analytics_cards.view`: `tile` (одна цифра по `option_value`) / `list` (все варианты полосками). Вид выбирается при генерации; у `tile` создаётся по строке НА КАЖДЫЙ вариант.

#### ⚠️ Никакой автогенерации «всё подряд» — клиент выбирает поля сам

Кнопка «Собрать автоматически» тащила все 30 разрезов и **плодила мусор**: один и тот же вопрос («Готовы выступать спикером?», «Сколько вам лет?») заведён отдельной строкой `survey_questions` в КАЖДОЙ из 4 анкет клиента → по четыре одинаковых квадратика. Плюс числовые с россыпью «21 — 1 человек, 22 — 1 человек». Владелец: *«мне не нужны лишние поля — нужно то, что нужно мне»*.

Теперь `POST /autofill` принимает `{keys: ['field:3','question:24'], view}` — ровно выбранные разрезы. UI: окно **сначала «откуда» (поля контакта / конкретная анкета), потом галочки на вопросах**. Считаем в рамках ОДНОЙ анкеты, аудитории зрителей и номинантов не смешиваются; `analytics_cards.survey_id` + название анкеты в подписи карточки — иначе четыре одинаковых вопроса на дашборде не различить. Без `keys` берутся все `AUTO_KINDS` (`select`/`multiselect`/`bool`/`number`/`scale`), но UI так больше не делает.

⚠️ У числовых разрезов с числом значений > `_NUMERIC_BREAKDOWN_LIMIT` (15) разбивка не рисуется — остаются среднее и размах. У «Сколько вам лет» иначе полсотни строк по одному человеку.

#### Клик по цифре — «кто эти люди»

Любая цифра кликабельна → список (имя, почта, телефон, TG) + выгрузка CSV (`;` и BOM — для Excel). `card_people` в [analytics_cards.py](backend/app/services/analytics_cards.py), эндпоинты `/cards/{id}/people` и `/people.csv`. ⚠️ Считает **теми же правилами**, что и сама цифра (те же условия, тот же разворот мультиселекта) — иначе список разошёлся бы с числом, на которое нажали, и доверять дашборду стало бы нельзя. ⚠️ CSV качается через `fetch` с токеном в заголовке, а не `<a href>` — эндпоинт требует авторизации.

**Условия** — полный конструктор И/ИЛИ с группами ([ConditionBuilder.tsx](web/src/components/analytics/ConditionBuilder.tsx)), дерево в `analytics_cards.filters` JSONB. Глубина ограничена `_MAX_DEPTH=5`. Нераспознанный узел даёт `TRUE`, а не выкидывает людей из подсчёта.

⚠️ `analytics_cards.ref_id` **намеренно без FK** — источника два, а FK смотрит в одну таблицу. Удалённый разрез отдаётся как `missing: true`, битый — как `error`; один сломанный квадратик не роняет весь дашборд.

⚠️ Перетаскивание — нативный HTML5 DnD, `draggable` включается **ТОЛЬКО когда мышь на ручке ⠿** (иначе браузер тащит карточку при работе с полями конструктора). Шаг `sort_order` = 10.

**API** ([analytics_dashboards.py](backend/app/api/analytics_dashboards.py)): `GET /analytics/sources` (справочник разрезов + операторы), `GET/POST/PATCH/DELETE /analytics/dashboards[/{id}]`, `GET /analytics/dashboards/{id}` (квадратики уже с цифрами), CRUD `/cards`, `/cards/reorder`, `/cards/autofill`. Гейт — только на ЗАПИСЬ («смотреть можно, менять нельзя»); ассистенту с ограниченными правами — 403. Фронт — `api.analytics.*`.
### Анкеты + дополнительные поля контакта (миграция 280 от 2026-08-12, ПРОД)

Свои анкеты вместо GetCourse. Там анкету нельзя было просто отправить: чтобы её заполнили, приходилось отдельно собирать страницу с формой. У нас анкета сразу даёт **готовую ссылку** `pluson.ru/f/{slug}` + по одной на каждую подключённую площадку (TG/VK/MAX) — как у лид-магнитов.

**⚠️ Поле анкеты и дополнительное поле контакта — ОДНА сущность** (`contact_fields`). «Доход», «Ниша», «Статус» — постоянные свойства человека: поле создаётся ОДИН раз на кабинет и сразу существует у всех контактов (пустым), живёт в карточке, фильтрует базу. Анкета его заполняет — два списка одного и того же клиенту вести не придётся. Значение текущее — `contact_field_values` UNIQUE(contact_id, field_id); история ответов отдельно, в `survey_answers`.

**Типы вопросов:** текст, длинный текст, число, дата, **шкала 1–10**, один вариант, несколько вариантов, да/нет. **Файлов нет намеренно** (решение владельца).

**⚠️ Анкета сама подарки НЕ выдаёт и на события не регистрирует.** Выдача включается ТОЛЬКО со стороны подарка — `lead_magnets.require_survey_id` / `lead_magnet_packages.require_survey_id` (по умолчанию NULL, существующие воронки не тронуты). Поэтому цикл «анкета выдаёт подарок, который требует эту же анкету» невозможен by design. Порядок в воронке: **подписка на канал → анкета → файл**.

**⚠️ Человека не бросаем со «спасибо».** В ссылке на анкету зашиты `contact_id`, номер подарка и площадка (`survey_link_for_run`), поэтому после отправки подарок выдаётся сразу — ссылкой на странице И сообщением в бот той площадки, откуда человек пришёл. Материалы собираются ТОЙ ЖЕ `_materials_for_run`, что и обычная воронка — второй механики выдачи нет, плейсхолдеры реф-кодов не разъезжаются.

**⚠️ Шлагбаум проверяет ФАКТ ответа, а не факт настройки** — заполнил однажды, больше не спрашиваем. Единая точка [survey_gate.py](backend/app/services/survey_gate.py); в `run_check_subscription` добавлен статус `survey_required`, обработка — во ВСЕХ 3 ботах (TG [funnel.py](backend/bot/handlers/funnel.py), VK [vk_main.py](backend/bot/vk_main.py), MAX [max_webhook.py](backend/app/api/max_webhook.py)). Проверка fail-open: сбой не лишает человека подарка.

**⚠️ Известного человека НЕ переспрашиваем.** Пришёл по `?c={contact_id}` — имя, почта, телефон и уже известные значения полей подставлены. В анкете клиента из 6 вопросов 5 были контактными; в GetCourse их вводили заново, потому что форма человека не знает. Незнакомый заполняет и становится новым контактом (`find_or_create_contact` — своих SELECT по email не писать).

**⚠️ Никаких вебхуков.** Анкета на нашем же сервере, ответ пишется в нашу базу тем же кодом — «заполнил ли» узнаём запросом, а не оповещением.

**Аналитика как в Google Forms:** по каждому вопросу проценты И абсолютные числа, полоски-диаграммы; у шкалы и числа — средняя. ⚠️ Процент считается **от ответивших на вопрос**, а не от всех заполнивших: необязательный могли пропустить, иначе сумма не сошлась бы в 100.

⚠️ **`options` разворачивать при отдаче** — asyncpg отдаёт JSONB **строкой**, фронт получал строку и не мог отрисовать варианты (хелперы `_jsonb`). При новой точке отдачи вариантов — не забыть.

**API:** кабинет `/api/v1/surveys*` + `/api/v1/contact-fields*` ([surveys.py](backend/app/api/surveys.py)), публичный `/api/v1/public/surveys/{slug}` + `/submit` ([surveys_public.py](backend/app/api/surveys_public.py)), значение поля вручную — `PUT /contacts/{id}/fields`. Фильтр базы — `field_filter=id:значение` в общем `_build_contacts_filter`, поэтому работает и в списке, и в CSV-выгрузке. Фронт: список [dashboard/surveys](web/src/app/dashboard/surveys/page.tsx), редактор и заявки — [dashboard/surveys/[id]](web/src/app/dashboard/surveys/%5Bid%5D/page.tsx), публичная [f/[slug]](web/src/app/f/%5Bslug%5D/page.tsx), api-группы `api.surveys.*` / `api.contactFields.*`.

⚠️ **Фича `surveys` заводится миграцией 337**, а не только руками на проде: до неё код требовал фичу, которой не было ни в одной миграции — на чистой базе анкеты не открылись бы ни у кого. Тарифы: **Экстра (`vip`) и `admin`**.

⚠️⚠️ **«Обработано» + «Заметка» заводятся при СОЗДАНИИ анкеты** (`create_survey`, 26.09.2026). Миграция 338 добавила их только существовавшим анкетам, и новые из кабинета создавались без них — заявки было нечем отмечать. Догнали миграцией 518. Новая точка создания анкеты — заводить оба поля и там (как в [solutions.py](backend/app/api/solutions.py)).

⚠️⚠️ **Удаление анкеты, стоящей в форме заявки** (26.09.2026). `request_forms.survey_id` — `ON DELETE RESTRICT`, и `DELETE /surveys/{id}` падал 500-й молча: анкету из готового решения (оно само заводит форму заявки) удалить было нельзя. Теперь без `?force=true` — 409 `{code: "survey_in_request_form", message}` со списком событий/продуктов; кабинет спрашивает «удалить вместе с формой заявки?» и повторяет с `force` — форма и анкета удаляются одной транзакцией.
### Дашборды анкеты — тот же движок, вторая точка входа (миграция 339)

`analytics_dashboards.survey_id` рядом с `event_id`. **Одно хранилище, два входа** (решение владельца): дашборд, созданный в анкете, виден и в «Аналитике»; созданный в «Аналитике» с выбором анкеты — виден внутри анкеты. Событийные при этом остаются только внутри события — там их и настраивают.

Каждой анкете создан дашборд **«Обработка заявок»** с двумя плитками.

⚠️⚠️ **Плитки «Да»/«Нет» НЕ РАБОТАЮТ** — на этом уже ошиблись (миграция 339, исправлено 340). Снятая галочка ответ удаляет, поэтому «Нет» всегда показывало ноль, и главной цифры — сколько осталось разобрать — не было. Правильно: **«Обработано»** — плитка без варианта, **«Не обработано»** — плитка с условием «поле не заполнено».

⚠️ Ради второй пришлось научить движок особому случаю (`_selects_unanswered` в [analytics_cards.py](backend/app/services/analytics_cards.py)): когда условия сами отбирают неответивших, «сколько ответили» всегда ноль, и считать надо всех прошедших условия. **Список людей за цифрой правится так же** — иначе он разошёлся бы с числом, на которое нажали.

⚠️ **`compute_tile` / `compute_card` / `card_people` получили `survey_id`** — дашборд анкеты считает только заполнявших ЭТУ анкету. Без него «не обработано» считалось от всей базы (7346 человек при 135 заявках).

⚠️ **`GET /analytics/sources?survey_id=` сужает разрезы до вопросов одной анкеты** — у клиента их под сотню, и одинаковые вопросы разных анкет не различить. Поля контакта остаются: ими режут ответы.

⚠️ **`analytics_dashboards.layout`** (`cards` | `columns`) — вид показа. Колонками: в шапке цифра, внутри список людей. **Сворачивается СПИСОК, шапка остаётся** — иначе на телефоне до соседней колонки пришлось бы листать сотни строк.

### Личные переписки «Диалоги» — история ЛС + ответы из дашборда (миграция 160 от 2026-06-21, НА ПРОДЕ)

**Зачем.** Раньше личные сообщения людей боту/сообществу клиента нигде не сохранялись — только летело уведомление `#user_message` в TG-канал организатора. Теперь клиент видит ВСЮ историю переписки 1-на-1 (что пишет человек / что отвечает бот / что отвечает он сам) и **отвечает прямо из кабинета** через свои боты TG/VK/MAX, может править и удалять свои сообщения (реально у получателя на платформе).

**⚠️ Отдельно от `event_chat_messages` (миграция 152)** — та про ГРУППОВЫЕ чаты событий и подсчёт баллов. `direct_messages` — про ЛИЧНЫЕ переписки.

**Архитектура хранения (сервер маленький по RAM):**
- **Текст** — в Postgres (`direct_messages`), лёгкий и быстрый.
- **Медиа** (фото/видео/документ) — в R2 по ключу `clients/{client_id}/dialogs/{contact_id}/{message_id}/{uuid}.{ext}` (новый kind `dialog_media` в [r2_storage.build_key](backend/app/services/r2_storage.py)), в БД только `media_url`+`media_kind`. Считается в квоту клиента (`storage_used_bytes` + `client_files`). Структура «по клиенту → по контакту» — папка контакта целиком переносима.
- **Голосовые НЕ качаем** — только пометка `media_kind='voice'`, бот отвечает «пишите текстом» (`VOICE_REPLY`). Запретить отправку голосовых на стороне бота технически нельзя ни на одной платформе → авто-ответ + не хранить файл.

### ⚠️ Резолв контакта — ВСЕГДА через `upsert_contact_with_identity` (2026-07-29, ПРОД)

**Единая точка опознания человека во ВСЕХ формах и точках входа** — [`upsert_contact_with_identity`](backend/app/services/contact_merge.py). Своих `SELECT ... FROM contacts WHERE email = ...` не писать: каждая самодельная версия по-своему решает, кого считать одним человеком, и плодит дубли.

**Что она делает (в этом порядке):**
1. Идентичность (`platform_users`) уже есть → берём её `contact_id`, дописываем пустые поля.
2. Передан **`known_contact_id`** (contact_id зашит в ссылку: `?c=`, `_ct{id}`, deeplink) → новая идентичность цепляется к ЭТОМУ контакту. Это главный приём против дублей при переходе между площадками: зарегался в VK → перешёл в TG по своей ссылке → TG становится ещё одной `platform_users` внутри того же контакта.
3. Иначе автомердж по `email_normalized` / `phone_normalized`, затем fallback по TG-нику (`lookup_telegram_username`).
4. Не нашли — создаём контакт.

**⚠️ Защита от гонок встроена** — `pg_advisory_xact_lock` по `(client_id, platform, platform_user_id)`. Двойная отправка формы или повторный `event_start` из Mini App не создадут второй контакт-сироту «Без имени».

**⚠️ Данные указывают на РАЗНЫХ людей → спрашиваем человека, а не решаем сами.** Email может принадлежать одному его контакту, а телефон — другому. Молча взять первый нельзя (заказ уйдёт не тому), слить автоматически — тем более. Во всех формах, где человек вводит данные руками, зовём **`find_contact_candidates`** из [contact_merge.py](backend/app/services/contact_merge.py): нашлось больше одного — отдаём `{need_choice: true, candidates: [...]}` и показываем экран «Это вы?» с ЗАМАСКИРОВАННЫМИ данными (`mask_email`/`mask_phone` — по чужому email нельзя подсмотреть чужой телефон). Выбор приходит как `chosen_contact_id`, «я здесь впервые» — как `force_new`. ⚠️ Эта логика живёт ТОЛЬКО в `contact_merge.py`. Своей копии «найти кандидатов» в модуле-потребителе быть не должно — она разъедется с остальными формами. Автослияния нет: ручное — кнопка «Объединить» в карточке контакта.

**Где уже применяется:** регистрация из вебинарной комнаты ([`register_event_from_deeplink`](backend/app/services/webinar_service.py)), форма заказа тарифа ([`event_orders.py`](backend/app/api/event_orders.py)), воронки лид-магнитов, боты TG/VK/MAX, вебхуки интеграций.

Поэтому: плашка «не закрывайте окно», `beforeunload`-вопрос браузера и кнопка **«Остановить»** (раньше «Отмена» на время работы блокировалась, и прервать импорт было нечем, кроме закрытия вкладки — ровно тем способом, от которого предупреждаем). Прерванный импорт помечается в итоге отдельной янтарной плашкой, а не зелёным «завершён».

⚠️ **В кнопке показываем СДЕЛАННОЕ**: «19% · 2 000 из 10 469 · 72 с». Раньше стояло общее число строк файла — по нему нельзя понять, сколько уже прошло.

⚠️ **Ники, которые уже есть в базе, у Telegram не спрашиваем** (`usernames_already_known`). Повторный импорт того же файла заново гонял тысячи `getChat` ради данных, лежащих в БД: на 10 000 человек это лишние минуты **до** начала записи. Нет колонки с никами вовсе — фронт заранее предупреждает, что загрузка будет дольше, и называет примерный срок.

⚠️ **Повторный импорт того же файла безопасен** — контакт ищется по `telegram_id`, дубль запрещён ограничением `UNIQUE(client_id, platform_slug, platform_user_id)`. Но колонка `subscribed` **перетирается по файлу**: если человек за это время отписался, а в файле у него `1` — он снова станет подписанным.
### Архитектура дашборда (зафиксировано 2026-04-25)

**Концепция:** дашборд = модули. **Реферальная программа — не отдельная сущность**, а вкладка внутри каждого события. Раздел «Рефералки» из сайдбара убирается.

**Сайдбар:**

**База** (видна всегда, общая для клиента):
- Контакты — `contacts` (человек), карточка с группами по платформам и блоком «Каналы»
- Коллабораторы — `collaborators` с FK `contact_id → contacts`
- **Лид-магниты** — общая база per-client: `name`, `description`, `url`. Используется в реф-программе любого события.
- **Каналы** (новое, миграция 036) — CRUD по `channels`. Боты Telegram, группы VK, MAX-каналы клиента. С формы выбирается платформа (FK на `platforms`), задаётся `bot_token`/`handle`/`display_name`.

**События:**
- **Мероприятия** — базовый раздел, у всех клиентов. Покрывает вебинары, уроки в записи, нетворкинги, эфиры, мастер-классы. Все они — записи в `events` с разным `module_slug`.
- **Конференции** — опциональный модуль (расширенные настройки: спикеры, программа, услуги, промо-партнёры). Живёт в отдельном разделе дашборда `/dashboard/conferences` и в этой переустройстве не затрагивается.
- **Премии** — опциональный модуль (скоро)
- **Турниры** — опциональный модуль (скоро)

**Карточка Мероприятия — вкладки:**
1. **Основное** — название, описание, даты, лендинг URL, адрес (одно поле — либо URL стрима, либо офлайн-адрес)
2. **Афиши** — список изображений с ориентацией (горизонтальная/вертикальная), несколько штук. Используются на лендинге, в рассылках, в шеринге.
3. **Реф-программа** — три подвкладки в порядке:
   - **Подарки** — пороги (1/3/10 друзей и т.д.) → к каждому свой `lead_magnet_id` + опциональный сертификат (картинка)
   - **Материалы** — изображения (выбор из афиш события + загрузка своих) + текст-анонс. Готово для шеринга участником.
   - **Шаблоны** — текст приветствия (включает список всех подарков) + тексты выдачи каждого подарка от бота
4. **Участники** — список зарегистрированных + фильтр-таблетки «Все / Зарегистрированы / Не зарегистрированы» со счётчиками + поиск + чекбокс «Зарегистрирован» в каждой строке (ручное переключение `event_participants.is_registered`). Тот же UI используется во вкладке «Участники» конференции.
5. **Рассылки** — шаблоны и очередь, на это конкретное мероприятие

**Ручное управление статусом участника:**
- `event_participants.is_registered` — переключается из UI чекбоксом в строке участника. Двусторонне (можно поставить и снять).
- `event_participants.is_in_chat` — только автоматически (через Salebot), руками **не** правится.
- **Удаление участника из события** — иконка-корзина в строке + `confirm()`. Удаляется только `event_participants` (контакт, TG-аккаунт, подписки, участия в других событиях остаются). Каскад: `gift_issuances` этого участника удаляются, `referrer_participant_id` у других обнуляется, `raffle_tickets.pluson_participant_id` → NULL по FK.
- API: `PATCH /api/v1/events/{event_id}/participants/{participant_id}` `{ is_registered: bool }`, `DELETE /api/v1/events/{event_id}/participants/{participant_id}`. Список — `GET /api/v1/events/{id}/participants?registered=all|yes|no` возвращает `participants[]` + `counts {total, registered, not_registered}`.
- Общий React-компонент: [`web/src/components/EventParticipants.tsx`](web/src/components/EventParticipants.tsx) — используется и в карточке мероприятия, и в `ParticipantsTab` конференции.

**Лендинг и адрес — у всех мероприятий** (не зависит от типа). Если не нужно — оставляют пустым.

**Сертификаты у подарков** — в MVP просто загрузка картинки. Идея на будущее: автогенерация именных сертификатов (аватарка участника + имя на шаблоне через Pillow + Telegram `getUserProfilePhotos`).
