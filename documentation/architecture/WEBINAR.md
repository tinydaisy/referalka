### Вебинарная комната — стрим через видеокодер + чат + продажи + аналитика (миграции 221-226 от 2026-07-16, ПРОД)

Своя вебинарная комната на pluson.ru — аналог GetCourse (тип трансляции «Видеокодер»). Полный план и список файлов — [documentation/WEBINAR-ROOM-PLAN.md](documentation/WEBINAR-ROOM-PLAN.md).

**Суть.** Zoom (Custom Live Streaming) / OBS → RTMP на наш **MediaMTX** ([media-server/](media-server/), отдельный процесс как `wa-bridge`) → HLS-плеер на `pluson.ru/webinar/{slug}/{day}` ([web/src/app/webinar/[slug]/[day]/page.tsx](web/src/app/webinar/%5Bslug%5D/%5Bday%5D/page.tsx), hls.js). Zoom НЕ встраивается в iframe (SDK запрещает) — идёт именно видеопоток по RTMP.

**Комната на ДЕНЬ события** (`webinar_rooms` по `event_id`+`day_number`, привязка к `conf_days`, не к событию целиком). Навигация вкладками дней в дашборде — как программа конференции.

**Гейт по фиче** (не по slug): `webinar_room` (Экстра/vip — своя комната), `webinar_link` (Профи/pro — только ссылка на стороннюю). Триалу зеркалятся обе (trial=pro).

**Что внутри комнаты:** HLS-плеер, живой чат (WebSocket + Redis pub/sub, [webinar_hub.py](backend/app/services/webinar_hub.py)), продающие блоки (`button`/`form`/`speaker_follow`/`gift` с таймингом `show_at_min`/`hide_at_min`), **умные формы** (известный контакт → 1 тап «Оставить заявку»; новый → поля; итог → контакт + **тег формы** = «группа» GetCourse через `contacts.tags`), реакции **👍/👎 по спикерам** (названия редактируются, 👎 отключаемая тумблером `show_down_reaction`, счётчики), **батлы** (спикеры выбираются из события, `webinar_battles`/`_players`), **опросы** (`webinar_polls`), кнопка **«Подписаться на спикера»** + плашка **«Сейчас выступает: {имя}»** (авто-смена по слоту `conf_sessions`, `current_speaker_ec_id`), **подарок спикера** по таймингу слота, удаление/бан участника (`webinar_banned`), редирект после эфира (`redirect_url`).

**Аналитика** ([webinar_analytics.py](backend/app/services/webinar_analytics.py)): heartbeat присутствия раз в минуту (`webinar_presence`, UNIQUE по room+contact/session+минута → уникальные онлайн), график по интервалам 5/10/20/40/60, метрики (всего уникальных, пик, комменты, клики, оплаты), **активность ПО КАЖДОМУ ЗРИТЕЛЮ** (`webinar_activity` с contact_id — фундамент геймификации), срез «онлайн в интервале → тег контактам».

**⚠️ `conf_sessions.speaker_id` = `event_collaborators.id`** (не `collaborators.id`) — текущий спикер по слоту резолвится через это. Владелец события — `event_owners (status='accepted')` (у `events` нет `client_id`). MediaMTX-хук `runOnPublish` дёргает `/api/v1/internal/webinar/stream/publish` (X-Bridge-Token) — валидирует ключ, ставит комнату `live`; неизвестный ключ → публикация отклонена.

**Роутеры:** клиентский `/api/v1/events/{id}/webinar` ([modules/webinar_room.py](backend/app/api/modules/webinar_room.py)), публичный `/api/v1/public/webinar/{slug}/{day}` + WS `/ws/webinar/{slug}/{day}` ([webinar_public.py](backend/app/api/webinar_public.py)). Фронт-дашборд — [WebinarTab.tsx](web/src/app/dashboard/conferences/%5Bid%5D/tabs/WebinarTab.tsx) + [WebinarAnalytics.tsx](web/src/app/dashboard/conferences/%5Bid%5D/tabs/WebinarAnalytics.tsx), api-группа `api.webinar.*`.

**⚠️ Источником может быть ЛЮБОЙ видеокодер, отдающий RTMP на наш адрес** — Zoom (Custom Live Streaming, есть уже на тарифе **Pro**, отдельный Zoom Webinars не нужен), OBS, Streamlabs, ffmpeg. MediaMTX не спрашивает, кто подключился: проверяется только ключ потока. **Яндекс Телемост, VK Звонки, Сферум и Google Meet НЕ подходят** — они умеют вещать только на свои площадки (Яндекс Эфир / VK Видео / YouTube), произвольный RTMP-адрес указать нельзя, а iframe у них запрещён. Из российских кастомный RTMP есть у **Контур.Толк** и **МТС Линк (Webinar.ru)** — тариф уточнять при подключении.

**⚠️ Установка MediaMTX — разовая, уже выполнена** ([media-server/README.md](media-server/README.md)): бинарник + systemd `plusson-mediamtx` + nginx `/hls/` + `ufw allow 1935` + общий секрет `WEBINAR_BRIDGE_TOKEN` (он же `MTX_BRIDGE_TOKEN` в `media-server/.env`). Порты: 1935 RTMP наружу, 8888 HLS и 9997 API — только localhost. ⚠️ Миграции вебинарки на проде — только через `sudo -u postgres` (роль plusson не владелец).
### Просмотр записи эфира + автовебинар (миграция 318 от 2026-08-19, ПРОД)

#### Запись и чат — на одном экране

Было: чат отдельной модалкой, простым списком **без времени**, а запись — только кнопкой «Скачать». По отдельности бесполезно: в репликах не видно, к какому моменту эфира они относятся, а в записи не видно, что писали зрители.

Теперь «▶ Смотреть» открывает `RecordingViewer` ([WebinarTab.tsx](web/src/app/dashboard/conferences/%5Bid%5D/tabs/WebinarTab.tsx)): слева видео, справа чат. У каждой реплики время от начала записи и часы по МСК, клик перематывает видео, звучащая сейчас реплика подсвечена, список едет за видео (галочка отключается).

⚠️ **`offset_sec` считает БЭКЕНД** от `webinar_sessions.started_at` (`GET /{day}/sessions/{id}/chat`) — на фронте эту арифметику не повторять, разъедется.

⚠️ **Сообщения с `session_id IS NULL` — это чат ВНЕ эфира** (люди заходят в комнату между запусками). К записи не относятся, в просмотрщик не попадают. На проде таких 38 за месяц — это норма, а не потеря.

#### Нарезка записи по спикерам (миграция 349 от 2026-09-05)

⚠️ **Ещё не на проде** — миграция написана, не накачена.

Эфир пишется ОДНИМ файлом: сначала настройка звука до «Начать эфир», потом открытие, потом выступления подряд. Целиком это никому не отдать — спикеру нужно СВОЁ выступление. Кнопка «✂️ Нарезать» у записи открывает редактор [RecordingCutter.tsx](web/src/components/webinar/RecordingCutter.tsx): плеер, таймлайн с вертикальными метками, «Расставить по программе дня», правка мышкой, «Нарезать».

⚠️⚠️ **Три РАЗНЫХ момента, не путать:**

| Что | Где | Знаем? |
|---|---|---|
| Поток пошёл (включили Zoom/OBS) | имя первого сегмента MediaMTX | да |
| **Начали эфир** (кнопка в кабинете) | `webinar_sessions.started_at` | да |
| Первый спикер заговорил | нигде | **нет** |

Первый кусок (проверка звука, «слышно меня») отрезается САМ: обе границы известны. Остаётся открытие внутри эфира — но и оно есть в программе слотом, поэтому раскладка по расписанию покрывает всё, а от клиента нужна только поправка сдвига.

⚠️⚠️ **`webinar_recordings.live_offset_sec` — на какой секунде ФАЙЛА нажали «Начать эфир»**, считается в `_live_offset_sec` ([webinar_recording.py](backend/app/tasks/webinar_recording.py)) из `started_at` и времени первого сегмента. **Физически ничего не обрезаем**: обрезка часового файла — это скачать гигабайты, пережать и залить обратно, а из обрезанного вернуть уже нечего. Смещение прибавляется в момент резки.

⚠️ **NULL ≠ 0.** NULL = посчитать не удалось (старая запись, куски удалены). Тогда раскладка по программе НЕ предлагается — метки только руками; ноль означал бы «эфир с первого кадра» и метки уехали бы молча на всю подготовку.

⚠️ **Метки в базе — секунды ОТ НАЧАЛА ЭФИРА**, как их видит клиент на таймлайне. Плеер живёт в секундах ФАЙЛА, поэтому фронт прибавляет `live_offset_sec` при перемотке, а бэкенд — при резке. Не смешивать.

⚠️⚠️ **Одна палочка = одна граница** (решение владельца): кусок идёт до следующей метки, `end_sec` от клиента НЕ приходит — его считает `save_cuts`. Перерывы не вырезаются, пауза попадает в кусок предыдущего спикера.

⚠️ **Границы считаются по ВСЕМ меткам, включая уже нарезанные** (`status='ready'`) — иначе конец черновика упёрся бы не туда, куски наложились бы, и спикер получил бы чужое выступление. Готовые куски правка не трогает: их файлы могли уже уйти людям.

⚠️ **Дедуп по секунде обязателен** — две метки в одну секунду дают кусок нулевой длины, на нём ffmpeg падает. Проверка стоит и в `program-marks` (параллельные залы в программе), и в `save_cuts`.

⚠️ **Режем `-c copy`, без пережатия** ([webinar_cut.py](backend/app/tasks/webinar_cut.py)): час на восемь частей — 10–30 секунд. Точная резка шла бы 30–60 минут на 2 ядрах и заняла бы процессор, на котором живут сайт, боты и рассылки. Плата — граница может уехать на пару секунд до опорного кадра; для выступлений незаметно.

⚠️ **`-ss` ДО `-i`** (быстрый поиск по индексу). После `-i` ffmpeg читает файл с начала до нужной секунды — на часовой записи это минуты вместо мгновения. Плюс `+faststart` (иначе плеер ждёт полной загрузки) и `-avoid_negative_ts make_zero` (иначе первые секунды чёрные).

⚠️ **Исходник НЕ удаляем** (решение владельца) — из кусков целое обратно не собрать, а нарезать могли криво. Удаление отдельной кнопкой.

⚠️ **Исходник скачивается ОДИН раз на все куски** — он весит гигабайты, качать заново под каждое выступление значит часы сети. И берётся из ТОГО хранилища, где лежит: у клиента может быть своё (та же развилка, что в `compress_recording`).

⚠️ **Куски регистрируются в `client_files`** — это гигабайты, без учёта квота их не видит (та же ошибка была когда-то у самой записи).

**Спикеру** его куски приходят в кабинет полем `my_recordings` (`GET /public/speaker-cabinet/me/materials`) — просмотр и скачивание. ⚠️ Отбор по `speaker_ec_id`: спикер видит СВОИ выступления, а не весь эфир.

**Записи покупателям тарифа «с записями» — НЕ сделано**, отложено по решению владельца.

**API:** `GET/PUT /{day}/recordings/{id}/cuts`, `GET /{day}/recordings/{id}/program-marks?shift_sec=`, `POST /{day}/recordings/{id}/cut`, `DELETE /{day}/recordings/{id}/cuts/{cut_id}` ([modules/webinar_room.py](backend/app/api/modules/webinar_room.py)), api-группа `api.webinar.cuts/programMarks/saveCuts/runCut/deleteCut`.

#### Автовебинар — запись крутится по расписанию как живой эфир

⚠️⚠️ **Отдельной сущности «автовебинар» НЕТ** — это та же `webinar_rooms` со `stream_type='auto'`. Чат, продающие блоки с таймингом (`show_at_min`), опросы, реакции и аналитика переиспользуются как есть. Заводить второй экран значило бы чинить вёрстку и логику в двух местах.

**Поля комнаты:** `auto_recording_id` (какую запись крутим, `ON DELETE SET NULL`), `auto_mode`, `auto_delay_min`, `auto_allow_seek`.

| Режим | Как работает |
|---|---|
| `schedule` | общий старт по расписанию — все зрители смотрят синхронно, как живой эфир |
| `on_signup` | свой старт у каждого, через `auto_delay_min` минут после захода (`webinar_auto_runs`) |

⚠️⚠️ **Стартовую секунду считает СЕРВЕР** (`_auto_payload` в [webinar_public.py](backend/app/api/webinar_public.py)), не браузер. Иначе зритель перезагружает страницу и начинает сначала — продающие блоки по таймингу теряют смысл.

⚠️ **Перемотка вперёд запрещена по умолчанию** (`auto_allow_seek=FALSE`) по той же причине.

⚠️ **Время расписания — строка `"HH:MM"` и всегда МСК** (`webinar_auto_schedule.at_time`), как `conf_sessions.start_time`. Иначе сдвиги часовых поясов. Ближайший старт ищется и за вчера тоже: запуск мог начаться до полуночи и идти сейчас.

⚠️ **Сценарий чата наполняется ИЗ ЖИВОГО ЭФИРА** — `POST /{day}/auto/chat-from-record?session_id=`. Полсотни реплик руками никто не напишет, а прошедший эфир уже дал настоящие вопросы в нужные моменты; тайминги берутся от `started_at` той сессии.

**API:** `GET/POST/DELETE /{day}/auto/schedule`, `/{day}/auto/chat`, `POST /{day}/auto/chat-from-record` ([modules/webinar_room.py](backend/app/api/modules/webinar_room.py)). Фронт — подвкладка «Автовебинар» (`AutoWebinarTab` в [WebinarTab.tsx](web/src/app/dashboard/conferences/%5Bid%5D/tabs/WebinarTab.tsx)), api-группа `api.webinar.auto*`.

⚠️⚠️ **Гейт — ОТДЕЛЬНАЯ фича `autowebinar` (только `vip` + `admin`), НЕ `webinar_room`.** Обычная вебинарная комната остаётся на **Профи и Триале** — забрать её значило бы отнять работающую функцию у 80 клиентов. Проверка стоит в 6 точках: сохранение комнаты со `stream_type='auto'`, CRUD расписания и сценария, перенос чата из эфира. Во фронте вкладка скрыта без фичи.

⚠️ **Фича НЕ зеркалится в триал** — правило «триал = Профи» касается фич, привязанных к `pro`; `autowebinar` привязан к `vip`, поэтому автозеркала не будет.
### Самозапись спикеров в слот программы + тема программы LIVE по topic_id (2026-06-30, коммит 604d5aa, ПРОД)

**Зачем.** Спикер сам занимает свой слот в программе турнира/конференции из своего кабинета, не дёргая организатора. И тема выступления в программе берётся **live** из карточки спикера — изменил тему → обновилось везде.

**Тема в программе живёт по `conf_sessions.topic_id`, не по замороженному `title`.** Везде, где показывается название слота, теперь `COALESCE(cst.topic, s.title)` через `LEFT JOIN conf_speaker_topics cst ON cst.id = s.topic_id` (`title` — fallback для слотов без спикера/темы). Поправлены ВСЕ точки: `program-public`, `sessions`, `sessions/day`, `regenerate_landing_data`, `landing_widget /program` ([conference.py](backend/app/api/modules/conference.py), [landing_widget.py](backend/app/api/landing_widget.py)) + рассылки `message_builder.py` (программа дня + custom-шаблон; `5min_before`/`speaker_intro` уже брали `cst.topic`). ⚠️ Паттерн `s.*, COALESCE(...) AS title` работает: asyncpg при дубле имени колонки берёт ПОСЛЕДНЕЕ значение. ⚠️ После того как спикеры разберут слоты — организатору нажать «Перегенерировать рассылки», чтобы `5min_before`/`speaker_intro` (per-session) подхватили новых спикеров.

**Модалка слота в дашборде** ([TournamentProgramTab.tsx](web/src/app/dashboard/conferences/%5Bid%5D/tabs/TournamentProgramTab.tsx), [ProgramTab.tsx](web/src/app/dashboard/conferences/%5Bid%5D/tabs/ProgramTab.tsx)): поле «Тема» вписывается руками ТОЛЬКО когда спикер НЕ выбран. Со спикером: 1 тема — подставляется сама (read-only превью), 2+ тем — селект выбора, 0 тем — жёлтая плашка «Тема будет уточнена позже, подставится автоматически когда спикер впишет». `saveSession`/`addSession` шлют `topic_id`; при пустой теме у выбранного спикера title = «Тема будет уточнена позже».

**Кабинет спикера → вкладка «Мой слот»** ([/speaker/<slug>](web/src/app/speaker/%5Bevent_slug%5D/page.tsx), компонент `SlotTab`, видна для role НЕ jury/organizer). Дни-вкладки (только дни со слотами), список слотов: занятые — имя + тема (мой подсвечен), свободные — radio-выбор. Кнопка «Сохранить» сверху (sticky) + надпись «Выберите день и свободный слот…». Предупреждение про live-тему. Защита: один слот на спикера, чужой занятый не тронуть, **пересадка** на другой свободный (старый освобождается), кнопка «освободить».

**Бэкенд** ([speaker_cabinet.py](backend/app/api/speaker_cabinet.py)): `GET /me/program` (этапы+дни+слоты, по каждому `is_mine`/`is_free`/`occupant_name`/`topic`), `POST /me/claim-slot {session_id}` (в транзакции `FOR UPDATE`: 409 если занят другим, иначе освобождает мой прежний слот в событии + занимает целевой `WHERE speaker_id IS NULL`), `POST /me/release-slot`. `session.se_id` = `event_collaborators.id` = `conf_sessions.speaker_id`. При claim, если у спикера ровно 1 тема (`conf_speaker_topics`) — проставляется её `topic_id`.

### Интеграция с Zoom — конференция дня одной кнопкой (миграция 444, 2026-09-18)

**Зачем.** Связка «зум → наша вебинарная комната» собиралась РУКАМИ и каждый раз одинаково: завести конференцию, открыть настройки, включить Custom Live Streaming, перенести туда RTMP-адрес и ключ потока из вкладки «Вебинар», вернуть ссылку входа в поле `speaker_join_url`. Четыре перекладывания строк между двумя вкладками браузера, и любое можно сделать неверно — выяснялось это в момент старта эфира, когда комната оказывалась пустой.

Теперь кнопка **«Создать конференцию Zoom»** во вкладке «Вебинар» (рядом с полем ссылки входа спикеров): создаёт конференцию, включает ей вещание на наш RTMP и подставляет `speaker_join_url`.

⚠️⚠️ **ЗУМ У КАЖДОГО КЛИЕНТА СВОЙ.** Конференции создаются в ЕГО аккаунте, не в аккаунте платформы: у Zoom лимит одновременных конференций на лицензию, и эфиры разных клиентов в одном аккаунте мешали бы друг другу. Клиент подключает зум сам — **Настройки → Интеграция**, кнопка «Подключить Zoom» → окно Zoom → согласие. Токены ложатся в `client_zoom_accounts` (одна строка на клиента, `UNIQUE client_id`).

⚠️ **В окружении — только ключи ПРИЛОЖЕНИЯ ПЛЮСОНа** (`ZOOM_CLIENT_ID`, `ZOOM_CLIENT_SECRET`, `ZOOM_OAUTH_REDIRECT_URI`), одно приложение на всех клиентов — как `vk_oauth_*` и `ig_app_*`. Тип приложения в Zoom Marketplace — **General App (OAuth)**, НЕ Server-to-Server: последний умеет работать только со своим аккаунтом и для клиентов не годится. Scopes: `meeting:write`, `meeting:read`, `user:read`.

⚠️ **Zoom выдаёт НОВЫЙ refresh-токен при каждом обмене и гасит прежний** — записывать надо оба (`_save_tokens` в [zoom_api.py](backend/app/services/zoom_api.py)). Сохранить только access значит потерять возможность обновиться, и клиент «отвалится» через час без видимой причины. Обновляем **заранее**, за 5 минут до истечения, а не по ошибке 401: запрос, начатый с токеном, истекающим через секунду, успеет протухнуть на полпути.

⚠️ **`stream_url` и `stream_key` передаются РАЗДЕЛЬНО** — Zoom склеивает их сам, ровно как `webinar_service.rtmp_url()` отдаёт базу без ключа. Передать адрес с ключом внутри значит получить путь `live/{key}/{key}`, которого плеер не найдёт: HLS ждёт `live/{key}`.

⚠️ **Настройка вещания ≠ запуск эфира.** Мы только настраиваем; кнопку «В эфир → Custom Live Streaming» ведущий всё равно жмёт в самом зуме, а дальше как раньше: MediaMTX ловит поток, `runOnPublish` ставит комнату `live`.

⚠️ **Custom Live Streaming требует у аккаунта КЛИЕНТА тариф Pro и выше.** На базовом конференция создастся, а вещать в комнату не будет. Поэтому тариф (`zoom_plan_type`: 1 — базовый, 2 — Pro, 3 — Business+) сохраняется при подключении и показывается в кабинете предупреждением — знать это нужно до эфира, а не во время.

⚠️ **Ошибка вещания НЕ откатывает конференцию.** Она создана и полезна сама по себе; ответ честно несёт `livestream_ok=false` и текст причины, а в базе лежит `webinar_rooms.zoom_livestream_ok`.

⚠️ **Пересоздание удаляет прежнюю конференцию** — иначе у дня копились бы дубли и спикеры расходились бы по разным. А вот **удаление комнаты дня конференцию в Zoom НЕ трогает**: её ссылка могла уже уйти спикерам, и снос заодно с комнатой сорвал бы эфир. Удаление конференции — отдельная кнопка (`DELETE /{day}/zoom-meeting`).

⚠️ **`zoom_start_url` наружу не отдаётся.** Открывший её становится ведущим конференции; в кабинете она не нужна — ведущий запускает эфир из своего зума. Спикеры идут по `speaker_join_url`.

⚠️ **`speaker_join_url` не дублируется.** Кнопка его заполняет, человек может поправить руками — и действует то, что в поле. Второе «настоящее» место для той же ссылки означало бы вопрос «какая из двух действует», а ответа на него нет.

⚠️ **Время конференции** — дата дня (`conf_days.day_date`, иначе `events.start_at`) + `open_time`, переведённые из МСК в UTC в единственном месте — роутере. Длительность из `close_time`; пусто → 4 часа (оборвавшаяся по таймеру конференция посреди эфира хуже запаса; Zoom по истечении ничего не выключает).

**Гейт — фича `zoom_integration`**, пока привязана только к скрытому тарифу `admin` (приём тот же, что у `speakers_call` в 438/439). Открыть клиентам = строка в `tariff_features` нужного тарифа, код не меняется. ⚠️ Фича добавлена и в условие показа вкладки «Интеграция» в настройках — иначе клиент с зумом, но без `partner_registration`, до неё не добрался бы.

**Таблицы:** `client_zoom_accounts` (токены, email/тариф аккаунта, `pending_state` для OAuth с TTL 10 минут, `refresh_failed_at`/`refresh_error` для «подключите заново»), поля `webinar_rooms.zoom_*`.

**API:** `GET/DELETE /api/v1/clients/me/zoom`, `GET /oauth-url`, `GET /oauth-callback` (без авторизации — Zoom не пересылает куки, клиент опознаётся по `state`), `POST /check` ([client_zoom_settings.py](backend/app/api/client_zoom_settings.py)); `POST/DELETE /api/v1/events/{id}/webinar/{day}/zoom-meeting` ([modules/webinar_room.py](backend/app/api/modules/webinar_room.py)). Сервис — [zoom_api.py](backend/app/services/zoom_api.py). Фронт — [ZoomSettingsBlock.tsx](web/src/components/settings/ZoomSettingsBlock.tsx) во вкладке «Интеграция» и кнопка в [WebinarTab.tsx](web/src/app/dashboard/conferences/%5Bid%5D/tabs/WebinarTab.tsx), api-группы `api.zoom.*` и `api.webinar.createZoomMeeting`.

⚠️ **Про Россию.** Zoom ограничил работу с российскими юрлицами, оплата российскими картами не проходит. Если зум клиента оформлен на российскую компанию, доступ к API может отвалиться не по нашей вине — кабинет в этом случае покажет «подключите заново» (`refresh_failed_at`). Из российских сервисов кастомный RTMP есть у **Контур.Толк** и **МТС Линк** — при необходимости они встают рядом тем же интерфейсом, без переделки вебинарной комнаты.


## Экран «эфир завершён»: следующий день, предложение, автопереход (18.09.2026)

Было: «Вебинар завершён · Спасибо, что были с нами!» и молчаливый переход через
**4 секунды хардкодом**. Пришедший после эфира не узнавал ни про следующий день,
ни про предложение — просто улетал по ссылке, не успев прочитать.

Стало — три блока, каждый появляется только если есть что показать:

| Блок | Когда виден | Откуда данные |
|---|---|---|
| «Встречаемся завтра в 11:00 МСК на День 2» | есть следующий день программы | считает бэк, `webinar_public.py` |
| Подводка + кнопка предложения | задан `redirect_url` | `outro_offer_text`, `outro_button_label` |
| «Перейдём автоматически через N сек» | `outro_redirect_sec > 0` | счётчик на экране |

⚠️ **Кнопка и автопереход ведут в ОДНО место** — `redirect_url`. Отдельной
ссылки под кнопку нет намеренно (решение владельца).

⚠️ **Фразу про следующий день считает БЭК той же логикой, что
`{next_day_mention}` в рассылках** — следующий НОМЕР дня (`day + 1`), «завтра»
или дата по разнице `day_date`. Так текст на странице и в письме совпадают
дословно. Последний день → `next_day = null`, блока нет.

⚠️⚠️ **Мгновенный редирект при закрытии комнаты УБРАН** (`stream_ended` в
веб-сокете и резервный поллинг). Раньше зритель, досидевший до конца эфира,
улетал по ссылке за ноль секунд — то есть новый экран видели бы только
опоздавшие, а досидевшие никогда. Теперь оба пути показывают экран завершения,
а уводит уже он, по своему счётчику.

⚠️ **Поля заведены с ГОТОВЫМ текстом, а не пустыми** (требование владельца):
«А пока у нас для вас предложение» / «Смотреть предложение» / 15 секунд. Пустое
поле с подсказкой-плейсхолдером не даёт понять, покажется что-то в итоге или
нет. `DEFAULT` в миграции 441 + `UPDATE` для уже созданных комнат (задним
числом DEFAULT не проставляется) + `??` во фронте для ответов старого API.

`outro_redirect_sec = 0` — не переводить автоматически, только по кнопке.
Настройки — вкладка «Вебинары» → день → блок «Экран после завершения эфира».


## Кнопка «Скопировать настройки в другие дни» (18.09.2026)

Настраивать три дня подряд руками — работа на ровном месте: отличаются у них
обычно только афиша и время, а чат, реакции, форма входа и экран завершения
одинаковые. Кнопка рядом с «Сохранить», видна от двух дней.
Эндпоинт `POST /events/{id}/webinar/{day}/copy-settings`
([webinar_room.py](backend/app/api/modules/webinar_room.py)); без тела — во все
остальные дни, с `target_days` — в выбранные.

⚠️⚠️ **Список копируемых полей — БЕЛЫЙ (`_COPYABLE_ROOM_FIELDS`), а не «всё
кроме».** Перечисление исключений ошибается молча и в опасную сторону: новую
колонку забудут исключить, и она уедет в чужой день. Так уже вышло бы с `zoom_*`
— их добавили в таблицу позже.

**НЕ копируется намеренно:**

| Поле | Почему |
|---|---|
| `title`, `opens_at`, `starts_at` | своё у каждого дня |
| `stream_key`, `hls_url` | **уникальны**, на них держится раскладка записей (PLAN.md, «Один Zoom на все дни») |
| `speaker_join_url` | вход спикера — для него отдельная кнопка «во все дни» |
| `zoom_*` | встреча Zoom своя у каждого дня |
| `status`, `room_state`, `stream_active`, `started_at`, `ended_at`, `current_session_id`, `chat_cleared_at` | текущее состояние эфира, не настройка |
| `auto_recording_id` | конкретная запись автовебинара |

Афиши живут не в `webinar_rooms` (а в `event_posters` / `conf_days`), их
копирование не касается вовсе.

⚠️ **Дни без комнаты тоже получают настройки** — комната создаётся со СВОИМ
ключом потока. Иначе копирование молча пропускало бы ровно те дни, которые ещё
не открывали, а заметно это стало бы во время эфира.

⚠️ **Фронт перед копированием СОХРАНЯЕТ текущий день** — бэкенд копирует то, что
лежит в базе, а не то, что набрано в форме. Без этого кнопка разнесла бы по дням
прошлые значения. Та же логика, что у «Скопировать во все дни» для зум-ссылки.
