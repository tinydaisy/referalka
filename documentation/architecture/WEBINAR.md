### Вебинарная комната — стрим через видеокодер + чат + продажи + аналитика (миграции 221-226 от 2026-07-16, ПРОД)

Своя вебинарная комната на pluson.ru — аналог GetCourse (тип трансляции «Видеокодер»). Полный план и список файлов — [documentation/WEBINAR-ROOM-PLAN.md](documentation/WEBINAR-ROOM-PLAN.md).

**Суть.** Zoom (Custom Live Streaming) / OBS → RTMP на наш **MediaMTX** ([media-server/](media-server/), отдельный процесс как `wa-bridge`) → HLS-плеер на `pluson.ru/webinar/{slug}/{day}` ([web/src/app/webinar/[slug]/[day]/page.tsx](web/src/app/webinar/%5Bslug%5D/%5Bday%5D/page.tsx), hls.js). Zoom НЕ встраивается в iframe (SDK запрещает) — идёт именно видеопоток по RTMP.

**Комната на ДЕНЬ события** (`webinar_rooms` по `event_id`+`day_number`, привязка к `conf_days`, не к событию целиком). Навигация вкладками дней в дашборде — как программа конференции.

**Гейт по фиче** (не по slug): `webinar_room` (Экстра/vip — своя комната), `webinar_link` (Профи/pro — только ссылка на стороннюю). Триалу зеркалятся обе (trial=pro).

**Что внутри комнаты:** HLS-плеер, живой чат (WebSocket + Redis pub/sub, [webinar_hub.py](backend/app/services/webinar_hub.py)), продающие блоки (`button`/`form`/`speaker_follow`/`gift` с таймингом `show_at_min`/`hide_at_min`), **умные формы** (известный контакт → 1 тап «Оставить заявку»; новый → поля; итог → контакт + **тег формы** = «группа» GetCourse через `contacts.tags`), реакции **👍/👎 по спикерам** (названия редактируются, 👎 отключаемая тумблером `show_down_reaction`, счётчики), **батлы** (спикеры выбираются из события, `webinar_battles`/`_players`), **опросы** (`webinar_polls`), кнопка **«Подписаться на спикера»** + плашка **«Сейчас выступает: {имя}»** (авто-смена по слоту `conf_sessions`, `current_speaker_ec_id`), **подарок спикера** по таймингу слота, удаление/бан участника (`webinar_banned`), редирект после эфира (`redirect_url`).

**Аналитика** ([webinar_analytics.py](backend/app/services/webinar_analytics.py)): heartbeat присутствия раз в минуту (`webinar_presence`, UNIQUE по room+contact/session+минута → уникальные онлайн), график по интервалам 5/10/20/40/60, метрики (всего уникальных, пик, комменты, клики, оплаты), **активность ПО КАЖДОМУ ЗРИТЕЛЮ** (`webinar_activity` с contact_id — фундамент геймификации), срез «онлайн в интервале → тег контактам».

**⚠️ `conf_sessions.speaker_id` = `event_collaborators.id`** (не `collaborators.id`) — текущий спикер по слоту резолвится через это. Владелец события — `event_owners (status='accepted')` (у `events` нет `client_id`). MediaMTX-хук `runOnPublish` дёргает `/api/v1/internal/webinar/stream/publish` (X-Bridge-Token) — валидирует ключ, ставит комнату `live`; неизвестный ключ → публикация отклонена.

**Роутеры:** клиентский `/api/v1/events/{id}/webinar` ([modules/webinar_room.py](backend/app/api/modules/webinar_room.py)), публичный `/api/v1/public/webinar/{slug}/{day}` + WS `/ws/webinar/{slug}/{day}` ([webinar_public.py](backend/app/api/webinar_public.py)). Фронт-дашборд — [WebinarTab.tsx](web/src/app/dashboard/conferences/%5Bid%5D/tabs/WebinarTab.tsx) + [WebinarAnalytics.tsx](web/src/app/dashboard/conferences/%5Bid%5D/tabs/WebinarAnalytics.tsx), api-группа `api.webinar.*`.

**⚠️ Источником может быть ЛЮБОЙ видеокодер, отдающий RTMP на наш адрес** — Zoom (Custom Live Streaming, есть уже на тарифе **Pro**, отдельный Zoom Webinars не нужен), OBS, Streamlabs, ffmpeg. MediaMTX не спрашивает, кто подключился: проверяется только ключ потока. **Яндекс Телемост, VK Звонки, Сферум и Google Meet НЕ подходят** — они умеют вещать только на свои площадки (Яндекс Эфир / VK Видео / YouTube), произвольный RTMP-адрес указать нельзя, а iframe у них запрещён. Из российских кастомный RTMP есть у **Контур.Толк** и **МТС Линк (Webinar.ru)** — тариф уточнять при подключении.

**⚠️ Установка MediaMTX — разовая, уже выполнена** ([media-server/README.md](media-server/README.md)): бинарник + systemd `plusson-mediamtx` + nginx `/hls/` + `ufw allow 1935` + общий секрет `WEBINAR_BRIDGE_TOKEN` (он же `MTX_BRIDGE_TOKEN` в `media-server/.env`). Порты: 1935 RTMP наружу, 8888 HLS и 9997 API — только localhost. ⚠️ Миграции вебинарки на проде — только через `sudo -u postgres` (роль plusson не владелец).
#### ⚠️⚠️ HLS требует COOKIE — иначе чёрный экран у всех, кроме Safari (25.09.2026)

**Симптом.** У зрителей чёрный экран без видео и звука: в Chrome/Яндекс/Android — всегда, в Safari — «то работает, то нет» (после F5 часто не грузит). Выглядело как «плохие телефоны / слабый интернет / VPN» — не оно.

**Причина.** MediaMTX v1.19 выдаёт зрителю HLS-сессию **кукой**: мастер-плейлист отвечает `302` + `Set-Cookie: hlsSession=…`, а дочерний плейлист и сегменты **без этой куки отдают 401**. Проверка на проде: `/index.m3u8` → 200, `/main_stream.m3u8` → **401, стабильно 5 из 5**.

⚠️ **Поток при этом полностью исправен** — в логе `recording 2 tracks (H264, MPEG-4 Audio)`, запись пишется, муксер поднят. Ошибку надо искать на выдаче зрителю, а не в кодировщике.

Отсюда и разное поведение по браузерам — один корень, два симптома:

| Кто | Механизм | Было |
|---|---|---|
| Chrome, Яндекс, Android | hls.js грузит плейлисты через **XHR**, а XHR куки по умолчанию **не посылает** | не работало НИКОГДА |
| Safari / iOS | играет HLS **нативно**, `<video>` посылает куку сам | работало при входе, после F5 отваливалось (сессия уже `closed: inactive`) |

Отсюда же «вход после контактов ≠ Обновить»: при первом входе кука свежая, после перезагрузки плеер запрашивает плейлист заново, а сессии уже нет.

**Лечение — ДВЕ правки, работает только вместе:**

1. **`xhrSetup: xhr.withCredentials = true`** в конфиге hls.js ([page.tsx](web/src/app/webinar/%5Bslug%5D/%5Bday%5D/page.tsx)) — чтобы XHR посылал куку.
2. **Убран `add_header Access-Control-Allow-Origin "*"` из `location /live/` и `/hls/`** ([nginx-hls.conf](media-server/nginx-hls.conf)). MediaMTX сам отдаёт CORS с конкретным origin + `Allow-Credentials: true`, а наш заголовок приходил ВТОРЫМ. Браузер отбрасывает ответ с двумя разными CORS-заголовками, а с куками значение `*` **запрещено стандартом**.

⚠️⚠️ **Вернуть тот `add_header` обратно = снова чёрный экран, даже с `withCredentials`.** Разрешённые источники настраиваются в `mediamtx.yml` (`hlsAllowOrigin`), а не в nginx. Это тот же класс ошибки, что «перечисление папок ошибается молча»: заголовок выглядит безобидной страховкой, а ломает всё.

**Проверено на живом эфире 25.09.2026** (событие 89, день 2): Android MI 8 — 16 сегментов подряд, отдано 33,6 МБ, **0 ошибок 401**; Яндекс на iPhone — 8 сегментов, 0 ошибок. До правки у обоих на дочерний плейлист был только 401. Зритель подтвердил картинку на Android/MI Browser.

⚠️ **Что НЕ помогло** (не пробовать второй раз): `hlsTrustedProxies: [127.0.0.1/32]`, `hlsCDNSecret: ""` — cookie-проверка в v1.19 включена безусловно, этими параметрами не снимается. `hlsDirectory` (сегменты на диск, отдаёт nginx файлами — куки не нужны вовсе) выглядит правильным решением, но на живом потоке подтвердить не успели и откатили; вернуться к нему стоит отдельно, вне эфира.

⚠️ **Как диагностировать в следующий раз** — не по словам зрителя, а по `access.log`: `grep '/live/' /var/log/nginx/access.log` и посмотреть коды по браузерам (`MiuiBrowser`/`YaBrowser`/`Version\/26`). Видно сразу: `401` на `main_stream.m3u8` = эта болезнь, `200` на `.ts` = видео физически доехало. ⚠️ Сверять время: массовые 401 могут быть следом собственных экспериментов с рестартом MediaMTX, а не жалобой зрителей.

#### ⚠️ Отдельно, НЕ путать с cookie: «segment duration changed from 2s to 4s»

В логе MediaMTX бывает `WAR segment duration changed from 2s to 4s - this will cause an error in iOS clients`. К cookie отношения не имеет и правкой выше не лечится — это нестабильный интервал ключевых кадров у **кодировщика**. Даёт рывки/подвисания именно на iOS. Лечится в настройках Zoom/OBS (keyframe interval 2 с), а не в коде плеера.

#### ⚠️⚠️ Плеер зрителя: со звуком и БЕЗ паузы (19.09.2026, правило владельца)

**У зрителя в прямом эфире НЕТ штатных `controls`.** Панель браузера даёт паузу, перемотку и таймер «6:59» — как у записанного видео. В live это вредит: пауза эфир не останавливает, он продолжает идти, и после «play» человек смотрит ПРОШЛОЕ, не понимая, почему говорящий отвечает не на то. Вдобавок промах мимо маленькой иконки звука попадал по видео и ставил его на паузу.

Вместо неё — `LiveControls` ([page.tsx](web/src/app/webinar/%5Bslug%5D/%5Bday%5D/page.tsx)): только звук и полный экран. Плюс **автодогон живого края** — раз в 5 секунд и при возврате во вкладку: если отстали от конца буфера больше чем на 6 секунд (свернули вкладку, подвисла сеть, заснул телефон), перематываем вперёд. Порог 6 с = длина HLS-сегмента с запасом, меньше — дёргало бы картинку на обычном джиттере.

⚠️ **Стартуем со ЗВУКОМ, `muted` — только запасной вариант.** Раньше плеер всегда запускался беззвучно, и зритель сидел в тишине, не найдя, где включить звук. Просто убрать `muted` нельзя: браузеры блокируют автозапуск со звуком, и тогда не запустится НИЧЕГО — чёрный экран вместо тихого видео, что хуже. Поэтому `playWithSound`: сначала со звуком; заблокировали — беззвучно (видео идёт) плюс **крупная кнопка «Смотреть со звуком» во весь кадр**. Одно нажатие включает звук и запускает видео: зритель жмёт «плей» и ждёт, что сразу услышит, а не пойдёт потом искать звук. Кнопка во всю площадь именно потому, что по маленькой промахиваются.

#### Модерация, запрет ссылок, один голос (миграции 470-471 от 2026-09-19)

⚠️⚠️ **Эндпоинты модерации существовали с самого начала, но КНОПОК к ним не было нигде** — удалить сообщение или выгнать человека было физически нечем. Теперь кнопки в самом чате комнаты (✕ скрыть сообщение, 🚫 удалить из эфира), видны только организатору, появляются по наведению на строку.

⚠️ **Организатор опознаётся по токену КАБИНЕТА** (`_is_room_moderator`, поле `is_moderator` в ответе комнаты), а НЕ по `contact_id` из ссылки: тот приходит из адресной строки и подделывается тривиально — на нём нельзя строить право модерировать и обходить запреты. Токен идёт необязательным параметром: у зрителя его нет, и это норма, а не ошибка.

**`block_links` — запрет ссылок в чате** (галочка, по умолчанию выкл.). На организаторов НЕ действует: их ссылки — часть эфира (оплата, материалы). Зритель получает отказ по имени: «Имя! Ссылки в чате запрещены правилами вебинара», текст возвращается в поле ввода — набирать заново не нужно.

⚠️ **Ссылка ловится ШИРЕ, чем `http://`** (`has_link`): схема, `www.`, голый домен в известной зоне и `@хендл` — запрет обходят именно голым доменом («пиши в t.me/name»). Но ловить любое «слово с точкой» нельзя: под это попали бы «спасибо.мне понравилось» и «1.5», и чат встал бы у обычных людей. Отсюда список зон.

⚠️ **Ссылки в чате кликабельные** (`ChatText`) — раньше были просто текстом, и ссылка организатора на оплату не открывалась. Вставляются ТОЛЬКО через `<a>`, без `dangerouslySetInnerHTML`: текст пишут зрители, вставка их HTML — дыра для чужого скрипта. `rel="noopener noreferrer"` обязателен. Регулярка фронта и `has_link` бэкенда должны совпадать, иначе «отправить нельзя, а подсветить нечего».

⚠️⚠️ **`one_vote_per_person` — один голос спикеру** (галочка, по умолчанию выкл.). Счётчик реакций был `count + 1` на каждое нажатие: один человек накручивал сколько угодно. Голос пишется строкой в `webinar_votes`, защита — УНИКАЛЬНЫЙ ИНДЕКС, а не «SELECT, потом INSERT»: между двумя запросами помещается второе нажатие (двойной клик), и проверка пропустила бы оба. Два ЧАСТИЧНЫХ индекса вместо одного: в обычном UNIQUE значения NULL не конфликтуют между собой, и аноним (`contact_id IS NULL`) голосовал бы повторно бесконечно.

⚠️ **Ограничение по ОБЪЕКТУ, а не по реакции** — иначе один человек поставил бы и 👍, и 👎 одному спикеру. Голос привязан к `session_id`: после «Начать заново» голосование чистое.

⚠️ **Счётчики реакций у каждого спикера СВОИ** (`UNIQUE (room_id, speaker_id, reaction_key)`) — при смене спикера показываются его цифры, с нуля, если ему ещё не ставили. Сбрасывать ничего не нужно, чужие оценки не переносятся.

⚠️ **Батлы от накрутки защищены ВСЕГДА**, независимо от галочки: голоса лежат строками в `webinar_battle_votes` с уникальностью по (игрок, зритель), счётчики пересчитываются подсчётом строк. Повторное нажатие МЕНЯЕТ свой голос, а не добавляет новый.

### Просмотр записи эфира + автовебинар (миграция 318 от 2026-08-19, ПРОД)

#### Запись и чат — на одном экране

Было: чат отдельной модалкой, простым списком **без времени**, а запись — только кнопкой «Скачать». По отдельности бесполезно: в репликах не видно, к какому моменту эфира они относятся, а в записи не видно, что писали зрители.

Теперь «▶ Смотреть» открывает `RecordingViewer` ([WebinarTab.tsx](web/src/app/dashboard/conferences/%5Bid%5D/tabs/WebinarTab.tsx)): слева видео, справа чат. У каждой реплики время от начала записи и часы по МСК, клик перематывает видео, звучащая сейчас реплика подсвечена, список едет за видео (галочка отключается).

⚠️ **`offset_sec` считает БЭКЕНД** от `webinar_sessions.started_at` (`GET /{day}/sessions/{id}/chat`) — на фронте эту арифметику не повторять, разъедется.

⚠️ **Сообщения с `session_id IS NULL` — это чат ВНЕ эфира** (люди заходят в комнату между запусками). К записи не относятся, в просмотрщик не попадают. На проде таких 38 за месяц — это норма, а не потеря.

⚠️⚠️ **Но в ЖИВОМ чате их показывать ОБЯЗАТЕЛЬНО** (19.09.2026, живой эфир iViSiON-9). `chat_history` ([webinar_public.py](backend/app/api/webinar_public.py)) брал строго `session_id = current_session_id` — и всё, написанное ДО нажатия «Начать эфир», пропадало у каждого, кто открыл страницу после старта. Автор своих сообщений не терял и поэтому не понимал, что их не видят: они пришли ему по WebSocket и остались в памяти вкладки, а новая вкладка грузит историю с нуля. Люди пишут до начала почти всегда — ссылку открывают заранее. Теперь условие `session_id = $2 OR (session_id IS NULL AND at > chat_cleared_at)`; отсечка по `chat_cleared_at` обязательна, иначе «Начать заново» возвращал бы сброшенные сообщения после старта эфира.

#### Нарезка записи по спикерам (миграция 349 от 2026-09-05)

⚠️ **Ещё не на проде** — миграция написана, не накачена.

Эфир пишется ОДНИМ файлом: сначала настройка звука до «Начать эфир», потом открытие, потом выступления подряд. Целиком это никому не отдать — спикеру нужно СВОЁ выступление. Кнопка «✂️ Нарезать» у записи открывает редактор [RecordingCutter.tsx](web/src/components/webinar/RecordingCutter.tsx): плеер, таймлайн с вертикальными метками, «Расставить по программе дня», правка мышкой, «Нарезать».

⚠️⚠️ **Три РАЗНЫХ момента, не путать:**

| Что | Где | Знаем? |
|---|---|---|
| Поток пошёл (включили Zoom/OBS) | имя первого сегмента MediaMTX | да |
| **Начали эфир** (кнопка в кабинете) | `webinar_sessions.started_at` | да |
| Первый спикер заговорил | нигде | **нет** |

Первый кусок (проверка звука, «слышно меня») отрезается САМ: обе границы известны. Остаётся открытие внутри эфира — но и оно есть в программе слотом, поэтому раскладка по расписанию покрывает всё, а от клиента нужна только поправка сдвига.

⚠️⚠️ **`webinar_recordings.live_offset_sec` — на какой секунде ФАЙЛА нажали «Начать эфир»**, считается в `_live_offset_sec` ([webinar_recording.py](backend/app/tasks/webinar_recording.py)) из `started_at` и времени первого сегмента. **Физически ничего не обрезаем**: обрезка часового файла — это скачать гигабайты, пережать и залить обратно, а из обрезанного вернуть уже нечего. Смещение прибавляется в момент резки.

⚠️ **NULL ≠ 0.** NULL = посчитать не удалось (старая запись, куски удалены). Тогда раскладка по программе НЕ предлагается — метки только руками; ноль означал бы «эфир с первого кадра» и метки уехали бы молча на всю подготовку.

⚠️ **Метки в базе — секунды ОТ НАЧАЛА ЭФИРА**, как их видит клиент на таймлайне. Плеер живёт в секундах ФАЙЛА, поэтому фронт прибавляет `live_offset_sec` при перемотке, а бэкенд — при резке. Не смешивать.

⚠️⚠️ **Одна палочка = одна граница** (решение владельца): кусок идёт до следующей метки, `end_sec` от клиента НЕ приходит — его считает `save_cuts`. Перерывы не вырезаются, пауза попадает в кусок предыдущего спикера.

⚠️ **Границы считаются по ВСЕМ меткам, включая уже нарезанные** (`status='ready'`) — иначе конец черновика упёрся бы не туда, куски наложились бы, и спикер получил бы чужое выступление. Готовые куски правка не трогает: их файлы могли уже уйти людям.

⚠️ **Дедуп по секунде обязателен** — две метки в одну секунду дают кусок нулевой длины, на нём ffmpeg падает. Проверка стоит и в `program-marks` (параллельные залы в программе), и в `save_cuts`.

⚠️ **Режем `-c copy`, без пережатия** ([webinar_cut.py](backend/app/tasks/webinar_cut.py)): час на восемь частей — 10–30 секунд. Точная резка шла бы 30–60 минут на 2 ядрах и заняла бы процессор, на котором живут сайт, боты и рассылки. Плата — граница может уехать на пару секунд до опорного кадра; для выступлений незаметно.

⚠️ **`-ss` ДО `-i`** (быстрый поиск по индексу). После `-i` ffmpeg читает файл с начала до нужной секунды — на часовой записи это минуты вместо мгновения. Плюс `+faststart` (иначе плеер ждёт полной загрузки) и `-avoid_negative_ts make_zero` (иначе первые секунды чёрные).

⚠️ **Исходник НЕ удаляем** (решение владельца) — из кусков целое обратно не собрать, а нарезать могли криво. Удаление отдельной кнопкой.

⚠️ **Исходник скачивается ОДИН раз на все куски** — он весит гигабайты, качать заново под каждое выступление значит часы сети. И берётся из ТОГО хранилища, где лежит: у клиента может быть своё (та же развилка, что в `compress_recording`).

⚠️ **Куски регистрируются в `client_files`** — это гигабайты, без учёта квота их не видит (та же ошибка была когда-то у самой записи).

**Спикеру** его куски приходят в кабинет полем `my_recordings` (`GET /public/speaker-cabinet/me/materials`) — просмотр и скачивание. ⚠️ Отбор по `speaker_ec_id`: спикер видит СВОИ выступления, а не весь эфир.

**Записи покупателям тарифа «с записями» — НЕ сделано**, отложено по решению владельца.

**API:** `GET/PUT /{day}/recordings/{id}/cuts`, `GET /{day}/recordings/{id}/program-marks?shift_sec=`, `POST /{day}/recordings/{id}/cut`, `DELETE /{day}/recordings/{id}/cuts/{cut_id}` ([modules/webinar_room.py](backend/app/api/modules/webinar_room.py)), api-группа `api.webinar.cuts/programMarks/saveCuts/runCut/deleteCut`.

Scopes: `meeting:write`, `meeting:read`, `user:read`.

⚠️ **Фразу про следующий день считает БЭК той же логикой, что
`{next_day_mention}` в рассылках** — следующий НОМЕР дня (`day + 1`), «завтра»
или дата по разнице `day_date`. Так текст на странице и в письме совпадают
дословно. Последний день → `next_day = null`, блока нет.

⚠️⚠️ **Мгновенный редирект при закрытии комнаты УБРАН** (`stream_ended` в
веб-сокете и резервный поллинг). Раньше зритель, досидевший до конца эфира,
улетал по ссылке за ноль секунд — то есть новый экран видели бы только
опоздавшие, а досидевшие никогда. Теперь оба пути показывают экран завершения,
а уводит уже он, по своему счётчику.

⚠️ **Поля заведены с ГОТОВЫМ текстом, а не пустыми** (требование владельца):
«А пока у нас для вас предложение» / «Смотреть предложение» / 15 секунд. Пустое
поле с подсказкой-плейсхолдером не даёт понять, покажется что-то в итоге или
нет. `DEFAULT` в миграции 441 + `UPDATE` для уже созданных комнат (задним
числом DEFAULT не проставляется) + `??` во фронте для ответов старого API.

`outro_redirect_sec = 0` — не переводить автоматически, только по кнопке.
Настройки — вкладка «Вебинары» → день → блок «Экран после завершения эфира».


## Кнопка «Скопировать настройки в другие дни» (18.09.2026)

Настраивать три дня подряд руками — работа на ровном месте: отличаются у них
обычно только афиша и время, а чат, реакции, форма входа и экран завершения
одинаковые. Кнопка рядом с «Сохранить», видна от двух дней.
Эндпоинт `POST /events/{id}/webinar/{day}/copy-settings`
([webinar_room.py](backend/app/api/modules/webinar_room.py)); без тела — во все
остальные дни, с `target_days` — в выбранные.

⚠️⚠️ **Список копируемых полей — БЕЛЫЙ (`_COPYABLE_ROOM_FIELDS`), а не «всё
кроме».** Перечисление исключений ошибается молча и в опасную сторону: новую
колонку забудут исключить, и она уедет в чужой день. Так уже вышло бы с `zoom_*`
— их добавили в таблицу позже.

**НЕ копируется намеренно:**

| Поле | Почему |
|---|---|
| `title`, `opens_at`, `starts_at` | своё у каждого дня |
| `stream_key`, `hls_url` | **уникальны**, на них держится раскладка записей (PLAN.md, «Один Zoom на все дни») |
| `speaker_join_url` | вход спикера — для него отдельная кнопка «во все дни» |
| `zoom_*` | встреча Zoom своя у каждого дня |
| `status`, `room_state`, `stream_active`, `started_at`, `ended_at`, `current_session_id`, `chat_cleared_at` | текущее состояние эфира, не настройка |
| `auto_recording_id` | конкретная запись автовебинара |

Афиши живут не в `webinar_rooms` (а в `event_posters` / `conf_days`), их
копирование не касается вовсе.

⚠️ **Дни без комнаты тоже получают настройки** — комната создаётся со СВОИМ
ключом потока. Иначе копирование молча пропускало бы ровно те дни, которые ещё
не открывали, а заметно это стало бы во время эфира.

⚠️ **Фронт перед копированием СОХРАНЯЕТ текущий день** — бэкенд копирует то, что
лежит в базе, а не то, что набрано в форме. Без этого кнопка разнесла бы по дням
прошлые значения. Та же логика, что у «Скопировать во все дни» для зум-ссылки.

### Продающие блоки: «Повысить тариф» и «Лендинг продукта» (миграция 463, 2026-09-19)

В комнате можно было позвать на другое событие (`event_reg`), но нельзя было продать то, ради чего эфир и проводится. Клиент выкручивался блоком-кнопкой со ссылкой, набранной руками, — она устаревала молча, и узнавал он об этом из жалоб зрителей.

Новые `webinar_blocks.kind`: **`tariff_upgrade`** (тариф ЭТОГО события, поле `tariff_id`) и **`product_landing`** (продукт клиента, поле `product_id`).

⚠️ **Ссылку и подпись собирает БЭКЕНД** (`_fill_tariff_block` / `_fill_product_block` в [webinar_public.py](backend/app/api/webinar_public.py)), а не фронт. Иначе адрес страницы заказа и правило «домен организатора» жили бы в двух местах, и при смене домена клиента кнопка в эфире молча вела бы не туда. Тариф ведёт на `/e/{slug}/order/{tariffId}` (эта страница сама узнаёт контакт), продукт — на `/pr/{slug}`.

⚠️ **Цена и название тарифа читаются ИЗ БАЗЫ в момент показа**, а не замораживаются в блоке: клиент меняет цену перед эфиром, и кнопка обязана показать новую — иначе она разошлась бы с кассой молча.

⚠️ **Недоступное не показываем вовсе** (`_skip`): тариф выключен (`is_active=FALSE`) или удалён, продукт не опубликован — блок не отдаётся зрителю. Кнопка «купить» на «страница не найдена» посреди эфира читается как сломанный сайт.

⚠️ **`ON DELETE SET NULL`, а не CASCADE**: удалённый тариф не уносит блок с его таймингом и текстом — блок просто перестаёт показываться, и клиент видит, что нужно выбрать заново.

⚠️⚠️ **Чужой `tariff_id`/`product_id` отсекается на бэкенде** (`_assert_block_refs` в [modules/webinar_room.py](backend/app/api/modules/webinar_room.py), и при создании, и при правке): поле приходит из браузера, а внешний ключ следит только за существованием строки, не за тем, чья она. Тариф проверяется по `event_id`, продукт — по `client_id`.

⚠️⚠️ **Новый вид блока добавляется В ТРЁХ местах фронта зрителя** ([webinar/[slug]/[day]/page.tsx](web/src/app/webinar/%5Bslug%5D/%5Bday%5D/page.tsx)): фильтр `items`, ветка `btnRun` и (если поведение особое) `clickBlock`. Пропустить фильтр — блок молча не покажется, хотя в кабинете создан и виден.

**Переименование:** `event_reg` в интерфейсе теперь «Регистрация на **другое** событие» — прежнее название не отвечало на вопрос «на какое?», а блок зовёт на любое событие клиента из списка, не на текущее.

### ⚠️⚠️ Приложение Zoom: где настраивается и что где лежит (2026-09-23)

**Кабинет разработчика:** [marketplace.zoom.us/user/build](https://marketplace.zoom.us/user/build) — список приложений, наше называется **General app 738**. Если ссылка не открылась: [marketplace.zoom.us](https://marketplace.zoom.us) → правый верхний угол **Develop** → **Build App**. Вход под аккаунтом `margarita.forbs1@gmail.com` (тариф Pro — трансляция на сторонний RTMP требует Pro и выше).

⚠️ **Тип приложения — General App (OAuth), НЕ Server-to-Server.** Server-to-Server умеет работать только со своим аккаунтом и для клиентов не годится: у каждого клиента свой зум.

**Карта интерфейса** (новый build flow, обязателен с 14.09.2024 — старые инструкции из интернета не совпадут):

| Что нужно | Где лежит |
|---|---|
| Client ID / Client Secret | **Basic Information** → App Credentials |
| OAuth Redirect URL + Allow List | **Basic Information** → OAuth Information |
| Права доступа (scopes) | **Scopes** |
| Secret Token для вебхуков | **Features → Access**, рядом с Event Subscriptions |
| Кнопка установки себе | **Local Test** → Add App Now |
| **Deauthorization Endpoint URL** | **App Listing** — ⚠️ раздел появляется ТОЛЬКО после переключения Development → Production |
| Название, описания, иконка, скриншоты | **App Listing** (там же) |
| Technical Design Document | **Technical Design** (тоже только в Production) |

⚠️⚠️ **Событие деавторизации НЕ добавляется через Event Subscriptions.** Там только вебхуки конференций (Meeting, Webinar, Recording, User…) — раздела «App» в списке нет вовсе, и искать его там бесполезно (потеряли на этом время 22.09.2026). Деавторизация — отдельное поле на странице App Listing, потому что привязана к OAuth, а не к событиям.

⚠️ **В режиме Development вебхуки деавторизации не приходят вообще** — Zoom шлёт их только опубликованным приложениям. Проверить endpoint заранее нельзя, он заработает после публикации.

**Что вписано у нас:**
- OAuth Redirect URL: `https://pluson.ru/api/v1/clients/me/zoom/oauth-callback`
- Deauthorization Endpoint: `https://pluson.ru/api/v1/zoom/webhook`
- Scopes: `meeting:write:meeting`, `meeting:update:livestream`, `meeting:update:livestream_status`, `meeting:delete:meeting`, `user:read:user`

⚠️ **Галочка «Optional» у scope в интерфейсе — это НЕ «включить право»**, а «разрешить пользователю его не давать». Оставлять ПУСТОЙ: снятое клиентом право на трансляцию означало бы, что конференция создаётся, а в комнату не льётся.

**Ключи на сервере** (`/var/www/plusson/backend/.env`): `ZOOM_CLIENT_ID`, `ZOOM_CLIENT_SECRET`, `ZOOM_OAUTH_REDIRECT_URI`, `ZOOM_WEBHOOK_SECRET`.

### Публикация приложения в Marketplace — что требуется (справка)

Публикация нужна ровно для одного: чтобы **клиенты** подключали свои зумы. Пока приложение в Development, подключиться может только аккаунт владельца платформы.

⚠️ **Обновления ПЛЮСОНа повторной проверки НЕ требуют.** Она нужна, только если менять права доступа или сам листинг (описание, скриншоты).

**Обязательное для подачи:**
1. Переключатель вверху страницы **Development → Production**
2. **App Listing**: имя (≤50 символов, «Zoom» только в форме «X for Zoom»), short description (≤150), long description, иконка 160×160 (светлая и тёмная), скриншоты App Gallery (точный размер показывает форма загрузки), Deauthorization Endpoint
3. **Четыре ссылки — обязательно на своём домене**, Google Docs и Notion → отказ: Privacy Policy (`/privacy`), Terms of Use (`/offer`), Documentation (`/data-deletion` — там есть раздел про удаление данных Zoom), Support (`/support`, ⚠️ с часами работы и сроком ответа)
4. **Technical Design Document**: стек, архитектура, три подтверждения (TLS 1.2+, проверка подписи вебхуков secret token-ом, шифрование данных)
5. **Тестовые учётные данные** к кабинету ПЛЮСОНа + пошаговый план для проверяющего (⚠️ отсутствие тест-плана — причина отказа №1)
6. **Верификация домена** — TXT-запись в DNS либо HTML-файл

⚠️⚠️ **САНКЦИОННАЯ ПРОВЕРКА ПРИ ПОДАЧЕ.** Zoom требует платящий аккаунт разработчика либо данные юрлица «to comply with U.S. Government sanctions regulations» (официальная причина отказа №7). **Российская карта не проходит.** Прямого запрета для РФ в документации нет, но реалистичный путь — аккаунт на неподсанкционную юрисдикцию. Выяснять это НАДО ДО подготовки иконок и скриншотов.

⚠️ Сроки: первый ответ 3–7 рабочих дней, полный цикл от месяца — Zoom сам пишет, что мало кто проходит с первого раза.

⚠️ **Unlisted (без витрины, по ссылке) полное ревью тоже проходит.** Обойти проверку нельзя; облегчённый трек — только Publishable URL для ограниченного числа пользователей.

### ⚠️⚠️ Два набора ключей Zoom: Development и Production (23.09.2026)

У приложения в Zoom Marketplace **два независимых набора** Client ID / Client Secret — переключатель Development / Production вверху страницы приложения меняет и их. Это разные ключи, не синонимы.

| Режим | Client ID | Когда действует |
|---|---|---|
| Development | `3G2tykt1RZOpoDvIP5mmkQ` | пока приложение не опубликовано |
| Production | `gOUI78pcREa2Qs1vNV6FNw` | после одобрения и активации |

**Оба набора лежат в `/var/www/plusson/backend/.env`** в блоке `# --- ZOOM KEYS ---`: действующий раскомментирован, второй — комментарием рядом. Переключение = поменять местами комментарии и `systemctl restart plusson-api`.

⚠️ **Порядок важен.** Прописать production-ключи ДО одобрения нельзя: Zoom их ещё не принимает, и подключение сломается у тех, кто уже подключил зум. Прописать ПОСЛЕ активации, но забыть — приложение в витрине есть, а подключение отвечает ошибкой, и человек видит это первым.

Правильная последовательность: Zoom одобрил → переключаем ключи в `.env` → рестарт API → проверяем подключение в кабинете → только теперь жмём **Activate** в Zoom.

Именно поэтому на странице Publish выбран вариант **«I will manually activate my app»**, а не автоматическая активация: она включила бы приложение в момент одобрения (возможно, ночью), когда сервер ещё на старых ключах.

⚠️ **`Use Public Client OAuth` НЕ включать.** Это режим для приложений без сервера (мобильных, браузерных расширений), где секрет негде хранить. У нас секрет лежит на сервере — включение режима ослабило бы защиту без всякой пользы.

⚠️ **`ZOOM_WEBHOOK_SECRET` в окружении пока НЕТ** — вебхук деавторизации отвечает 503. Secret Token берётся в приложении: **Features → Access**, рядом с Event Subscriptions. Без него на ревью будет замечание.
